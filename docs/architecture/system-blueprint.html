QORA / RWA-Vault System Blueprint

Post-quantum anchored protocol for tokenised real-world assets with collateralised micro-lending at the PKR 1,000 scale. This set shows every block of the system, what goes in and comes out of each, how those outputs connect, and the technology under each block. Sandbox posture: mock fiat leg, test-net tokens, no real funds.

F1 · MS1

Asset onboarding: a gold lot becomes a token

sequenceDiagram
  autonumber
  actor P as Asset provider
  participant PC as Provider console
  actor C as Custodian
  participant V as pq-verifier (M2)
  participant AR as AssetRegistry (M3)
  participant T as ERC-3643 token
  participant B as anchor-batcher (M9)
  P->>PC: lot metadata, valuation basis, custodian
  PC->>AR: register(asset) puts it in PENDING
  C->>C: sign reserve attestation with ML-DSA-65 (Tier 1 key)
  C->>V: PQEnvelope action=attest, seq, reserveAmount
  V->>V: 7 named checks, nonce compare-and-increment in PostgreSQL
  V->>B: envelope hash as a leaf (Redis Stream)
  V->>AR: submit verified attestation
  AR->>AR: 4 clauses — signature valid, seq increasing, reserve ≥ supply, valuation fresh
  alt all four clauses hold
    AR->>AR: PENDING to LIVE
    AR->>T: minting allowed while attestedSupply ≤ reserveAmount
  else any clause fails
    AR-->>PC: revert names the failed clause, asset stays PENDING
  end
  B->>B: next epoch root goes to PQAnchor
F1b

AssetRegistry state machine

stateDiagram-v2
  direction LR
  [*] --> UNREGISTERED
  UNREGISTERED --> PENDING: register(metadata)
  PENDING --> LIVE: admit, 4-clause predicate passes
  PENDING --> UNREGISTERED: reject
  LIVE --> FROZEN: freeze by agent
  FROZEN --> LIVE: unfreeze

Minting is possible only in LIVE. Invariant checked on every mint and every attestation: attestedSupply ≤ reserveAmount.

F3

Envelope verification: seven checks, first failure wins

flowchart LR
  E[PQEnvelope + signature] --> C1{1 algorithm allowed for action}
  C1 -- pass --> C2{2 signer key active, not revoked}
  C2 -- pass --> C3{3 domain: chainId, contract, action}
  C3 -- pass --> C4{4 now inside validFrom..validTo}
  C4 -- pass --> C5{5 nonce = stored + 1}
  C5 -- pass --> C6{6 signature over zeroed envelope}
  C6 -- pass --> C7{7 payloadHash = executed payload}
  C7 -- pass --> OK([accept: execute + leaf to M9])
  C1 -- fail --> X([reject with the check name])
  C2 -- fail --> X
  C3 -- fail --> X
  C4 -- fail --> X
  C5 -- fail --> X
  C6 -- fail --> X
  C7 -- fail --> X

Cheap checks run first; the signature check (calls M1 verify through the Node addon) runs late. The adversarial replay suite asserts the name of the failed check, not just a rejection.

F4

Oracle round: five sources to one committed price

flowchart LR
  S1[Source 1] & S2[Source 2] & S3[Source 3] & S4[Source 4] & S5[Source 5] --> P[Poll in parallel, 3 s timeout]
  P --> D[Drop invalid or stale]
  D --> Q{Quorum ≥ 3}
  Q -- no --> R([Refuse: no round committed])
  Q -- yes --> M[Median]
  M --> T{Within ±10 % of 30-min TWAP}
  T -- no --> R
  T -- yes --> N{roundId and timestamp increase}
  N -- no --> R
  N -- yes --> SG[Sign round with ML-DSA-44]
  SG --> PO[(PriceOracle.sol)]
  PO --> X[Redis Stream price ticks to risk-engine]

The order is the security property: taking the median before the deviation test stops one corrupted feed from deciding whether a round is accepted. A stale price freezes new borrows but never blocks repay or withdraw.

F5 · MS3

Lending: borrow, price drop, buffer or liquidation

sequenceDiagram
  autonumber
  actor I as Investor
  participant W as PWA
  participant CM as CollateralManager
  participant LP as LendingPool
  participant PO as PriceOracle
  participant RE as risk-engine (M6)
  participant RB as ReserveBuffer
  participant L as Liquidator
  I->>W: lock vault shares, request loan
  W->>CM: Falcon-signed borrow intent (through pq-verifier)
  CM->>PO: last committed price p
  CM->>CM: HF = q × p × λ / D, require post-borrow HF ≥ 1.15
  CM->>LP: borrow, debt scaled by the global index
  PO-->>RE: price tick (Redis Stream)
  RE->>RE: recompute HF for every position
  alt 1.00 ≤ HF and HF below 1.15
    RE-->>W: alert borrower
  else 0.95 ≤ HF and HF below 1.00
    RE->>RB: propose buffer claim
    RB->>RB: per-epoch cap κ = 0.40 × B, one claim per position
  else HF below 0.95
    RE->>L: propose liquidation
    L->>CM: re-derive HF on-chain, revert if engine was wrong
    L->>LP: repay up to φ = 0.50 of debt, bonus decays over 20 blocks
  end

SHEET 6

Data contracts that glue the blocks

PQEnvelope: what each field stops

FieldAttack it removesEnforced by check
versionAmbiguous format in the signed bytesCodec rejects unknown versions
algorithmDowngrade to a retired primitive1 · algorithm allowed for action
signerSigning with an unregistered or revoked key2 · signer resolves to active key
chainId · contract · actionCross-chain, cross-contract and action-substitution replay3 · domain separator matches
validFrom · validToDelayed execution (90 s intents, 3,600 s attestations)4 · clock inside window
nonceSame-signer replay5 · nonce = stored + 1
signatureForgery; signed over the envelope with the signature zeroed6 · signature verifies
payloadHashExecuting a payload other than the one signed7 · payload hash matches

Post-quantum primitives and where each one is used

AlgorithmStandardPublic keySig / ciphertextUsed for
Falcon-512FIPS 206 draft897 B666 BTier 2 device keys, user intents, on-chain dispute verifier
ML-DSA-44FIPS 2041,312 B2,420 BOracle price rounds, server attestations
ML-DSA-65FIPS 2041,952 B3,309 BTier 1 service keys, custodian reserve attestations
SLH-DSA-SHA2-128sFIPS 20532 B7,856 BTier 0 root, offline ceremony only (pqctl)
ML-KEM-768FIPS 2031,184 B1,088 BEnvelope encryption, secure channels
ML-KEM-1024FIPS 2031,568 B1,568 BKey wrapping, long-term storage

For scale, ECDSA-P256 uses a 64-byte signature. PQ signatures are 10–100× larger, which is why the design verifies them off-chain and anchors only a 32-byte Merkle root per epoch. Past roughly 14 events per epoch this costs less gas than per-event ecrecover.
