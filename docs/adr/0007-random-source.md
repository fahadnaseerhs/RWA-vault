# ADR 0007 — Random source: OS CSPRNG natively, Web Crypto in WASM, fail closed

- **Status:** Proposed
- **Date:** 2026-08-20
- **Deciders:** Fahad Naseer, Hassan Attique, Fawaz Asif

## Context

§8.4 requires the operating-system CSPRNG in native builds and Web Crypto-backed
randomness in WASM, with no deterministic or test RNG reachable in production
builds. §5.3 additionally requires the browser build to fail closed when secure
randomness is unavailable.

Randomness enters M1 in three places, and they have different properties:

- **Key generation**, for all six primitives. A weak seed here is total and silent
  compromise, and it is unrecoverable — a Falcon device key generated from bad
  entropy stays bad for the life of the device record.
- **Hedged signing.** ML-DSA's signing procedure consumes fresh randomness in its
  hedged mode; Falcon consumes randomness for the salt and for Gaussian sampling.
  SLH-DSA-SHA2-128s signing is deterministic in the parameter set we use.
- **Encapsulation**, for the two ML-KEM parameter sets.

Conformance testing pulls in the opposite direction from all of this. ACVP vectors
for ML-DSA, ML-KEM and SLH-DSA supply the seed directly — `keyGen` takes ξ, ML-KEM
`encapDecap` takes m, ML-DSA `sigGen` supplies rnd — so those tests need a way in
that does not use the RNG at all. Falcon's Round 3 KATs are worse: they were
generated by driving the NIST AES-CTR-DRBG from a fixed seed, so reproducing them
requires that specific DRBG in place of the real one. A test hook is therefore
unavoidable, which makes "no deterministic RNG reachable in production" a build
problem rather than a coding-discipline problem.

## Decision

**One entropy path per target, taken from the `getrandom` crate, with no fallback.**

- **Native** (`x86_64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`): the OS CSPRNG —
  `getrandom(2)` on Linux, `BCryptGenRandom` on Windows — reached through
  `getrandom`, pinned in `Cargo.lock`.
- **WASM** (`wasm32-unknown-unknown`): `crypto.getRandomValues`, reached through the
  same crate's Web Crypto backend, enabled by whichever feature or `cfg` the pinned
  major version documents for that backend. A test asserts at runtime that the
  browser backend is the one in use — it draws repeatedly and fails if any draw
  errors or if any draw is all-zero — so a misconfigured backend is a red test
  rather than a silent weakness.
- **No userspace PRNG is seeded and reused.** There is no long-lived `ThreadRng`, no
  ChaCha stream reseeded on a timer, no entropy pool of our own. Every request goes
  to the OS or to Web Crypto. At this call volume the syscall cost is irrelevant and
  the reasoning is simpler: there is no state to fork, snapshot, or fail to reseed.

**Fail closed, everywhere.** An RNG error returns `RngFailure` (ADR 0006). It is
never retried in a loop, never silently downgraded, and never allowed to proceed
with a partially filled buffer. In the browser, `init()` probes the entropy source
during module initialisation and rejects if it is unavailable, so the API is never
handed to the PWA in a state where key generation would produce a weak key.

**Deterministic entropy is a separate, seed-taking API — not a swapped RNG.** Rather
than making the RNG pluggable, the conformance surface is explicit seed-taking
functions:

- `keygen_from_seed(algorithm, seed)` and, where the scheme needs it,
  `sign_deterministic(algorithm, sk, msg, rnd)` and
  `encapsulate_with_m(algorithm, ek, m)`.
- These are compiled only under `#[cfg(feature = "kat")]`.
- The Falcon Round 3 NIST AES-CTR-DRBG lives in `native/tests/` as test-only code.
  It is not in the library crate at all, in any configuration.

The `kat` feature is not enabled by any default, is not enabled by the `napi` addon
crate or the `wasm` crate, and is guarded at compile time:

```rust
#[cfg(all(feature = "kat", not(debug_assertions)))]
compile_error!("the `kat` feature must not be enabled in an optimised build");
```

Because §8.3 forbids comparing debug numbers with release acceptance results, the
conformance suite still needs optimised code. It gets it from a dedicated CI job
that builds with `--release` **and** an explicit `RUSTFLAGS` override acknowledging
the guard. That job's output is a test report only: **the release-artefact job is a
separate job that builds without the `kat` feature, and only its binaries are
checksummed, signed off, and published** (ADR 0008). A CI assertion fails the
release job if the `kat` feature appears anywhere in its resolved feature set.

## Consequences

**Good.** The production entropy path is one line of code per target with no
branching, no configuration, and no policy — which is the only kind of RNG code that
can be reviewed with confidence.

**Good.** Because the KAT hooks take a seed as an argument rather than replacing a
trait object, there is no injection point in the production API. Nothing can be
constructed at runtime that causes `keygen` to use attacker- or test-supplied
entropy; the deterministic functions are different functions, and in a release build
they do not exist.

**Good.** The all-zero draw check catches the specific WASM failure mode where a
misconfigured backend links a stub that returns success without writing bytes — a
failure that no amount of code review of our own crate would find.

**Costly.** Two CI jobs building the same code with different features, and a
discipline that only one of them may publish artefacts. If that discipline slips, a
`kat`-enabled binary could ship. The feature-set assertion in the release job is the
control, and it must be a hard failure rather than a warning.

**Costly.** Going to the OS for every draw is slower than a userspace PRNG. This is
measured rather than assumed — RQ1's keygen and signing latencies include it — and
at tens of events per epoch it will not be the term that matters.

**Costly.** Falcon's Round 3 KAT reproduction requires us to carry an AES-CTR-DRBG
implementation in the test tree. It is test-only and unreachable from the library,
but it is still cryptographic code we maintain. It is reviewed as such.

**Binding on M10.** M1 guarantees that the browser build sources entropy from Web
Crypto and fails closed. It does not and cannot guarantee what happens to the
generated key afterwards — IndexedDB storage, session cleanup, and the lifetime of
JavaScript-side copies are M10's, per the split the manual draws in §5.3.

## Alternatives considered

**A pluggable `RngCore` trait on the public API, with the OS RNG as default.**
Rejected. It is the conventional Rust design and it puts a runtime-reachable
injection point into key generation, which is the one operation where a wrong RNG is
unrecoverable and undetectable. Seed-taking functions behind a feature flag give the
tests everything they need without that point existing.

**An environment variable or config flag to select a deterministic RNG.** Rejected
outright: it makes the security property depend on deployment configuration, and
§8.4 requires a build-time guard specifically to avoid that.

**Seed a userspace CSPRNG (ChaCha20) once from the OS and draw from it.** Rejected:
it trades a syscall we can afford for fork-safety, reseeding and snapshot-restore
concerns that we would then have to reason about. The performance it buys is
irrelevant at this call volume.

**Let the WASM build fall back to a JavaScript PRNG when Web Crypto is absent.**
Rejected, and it is the failure mode §5.3 names. Every browser in the supported
matrix has `crypto.getRandomValues`; its absence means a non-secure context or an
environment we should not be generating a signing key in. Refusing to initialise is
the correct behaviour.

**Use ML-DSA's deterministic signing mode in production to remove signing-time
entropy.** Rejected: hedged signing is the FIPS 204 default and is the more robust
choice against fault attacks, and removing the entropy requirement from signing does
not remove it from key generation, so the RNG path has to be right regardless.
