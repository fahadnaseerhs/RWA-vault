# 🐞 → 🧭 T6.0 — Debugger Questions for the Researcher

Cases from [[T6.0 - Debugger Brief]] where the research does not say what should happen. **Nothing below has been changed in the code.** Each question gives the situation, what the code does now, and what is needed to decide it. Full run: [[T6 - Provider Onboarding Console#12. T6.0 — Debugger Report (2026-10-27)|§12]].

---

### Q1 — B13: how far into the future may `valuationTs` be? *(blocks the B13 fix)*
- **Scene:** the provider types `4102444800` (year 2100). Clause 4, `now − ts ≤ τ`, passes trivially. Today the file is accepted.
- **Known:** year 2100 must be rejected. A failing test exists for that case.
- **Not known:** where the line sits. Reject anything `> now`? Or allow `now + δ` for clock skew (and if so, what δ)? Reject outright, or warn? The validator only returns errors today, so a "warn" outcome would be a new kind of result.
- **Parity cost:** JSON Schema has no way to say "now", so this check can only live in the TS validator. That breaks D1 parity on purpose. Is that acceptable if the schema's `description` documents it? The alternative is a fixed upper bound (e.g. `maximum: 4102444799`), which the schema *can* express.

### Q2 — B10: how should the schema express the `uint256` limit? *(blocks the B10 fix)*
- **Known:** values above `2²⁵⁶−1` must be rejected, on both `intendedSupply` and `unitValue`. The TS fix is easy: `BigInt(v) <= MAX`.
- **Not known:** in JSON Schema, a string-pattern comparison against `115792…639935` is technically possible but would be a regex nobody can review. The options:
  - (a) Schema says `maxLength: 78` and TS does the exact check. The two validators then disagree only on 78-digit values above the max.
  - (b) Generate the exact pattern and test it.
  - (c) Accept the divergence and document it.
- **Related:** should `unitValue × intendedSupply` also be capped so that a `totalValue` computed downstream cannot overflow? Nothing in the research says.

### Q3 — B16: `treasuryWallet == token`: reject or warn?
- The brief says "rejected or warned". The validator has no warning channel, so this needs a decision. Either way it is TS-only: JSON Schema cannot compare two fields. That makes it the same parity question as Q1.

### Q4 — B4: are `gold-` (trailing hyphen) and `go--ld` (double hyphen) legal `assetId`s?
- Both are accepted today, by both validators, under the confirmed regex `^[a-z0-9][a-z0-9-]{0,31}$`. B3 of [[T6.0 - Researcher Answers]] confirmed that regex but never addressed these two shapes. Keep them, or tighten the regex to `^[a-z0-9]+(-[a-z0-9]+)*$` with the 32-char cap kept separately?

### Q5 — B14: format-only `currency`, or a real ISO 4217 list?
- `"XYZ"` is accepted (3 uppercase letters, not a real currency). Keep format-only, or add an allow-list (USD, EUR, GBP, AED, CHF…)? Note that `currency` goes into `metadataHash` (A2), so a typo becomes part of the asset's permanent identity.

### Q6 — Invisible-only strings
- A `description` of just `"​"` (zero-width space) or `"\u0085"` (NEL) passes both validators. Neither character counts as whitespace to `trim()` or `\S`. The value is useless, and it gets hashed into `metadataHash`. Reject (by requiring at least one visible character), or accept?

### Q7 — E1: where should a *missing* field point?
- Today `missing required field "description"` is reported at path `""` (the parent object), and a missing `attestor` at `/attestations/0`. This matches what Ajv does, but the brief's E1 says the path should point "at the actual offending field". A console that highlights `/description` needs the path to *be* `/description`. Keep the parent-path convention, or move the path to the missing field?
