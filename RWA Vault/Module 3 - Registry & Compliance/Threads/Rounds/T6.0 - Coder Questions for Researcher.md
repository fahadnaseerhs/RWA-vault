## Part A — Gaps that depend on T0.6 (`IAssetRegistry`)

### A1. How does the text `assetId` become the on-chain id?
- **Research says:** `"assetId": "gold-lot-001"` (a string) in §3.2, and `assetRegistry.stateOf(cfg.assetId)` / `register(assetId, …)` in §3.3. It doesn't say what type the contract takes.
- **Options:** (a) `bytes32` = the string right-padded (needs ≤ 32 bytes); (b) `bytes32` = `keccak256(bytes(assetId))`; (c) `string` on-chain.
- **Coder's provisional choice:** the schema caps `assetId` at 32 characters, so (a) and (b) both still work. Nothing in the schema commits to either.
- **Recommendation:** (b) keccak. Fixed size, no padding edge cases, and the readable slug stays in events/metadata.
- **Blocks:** T0.6 signature, T6.1a step 2, T6.1b's `stateOf` query.

### A2. Where does `metadataHash` come from? ⚠ real gap
- **Research says:** §3.3 step 2 calls `register(assetId, metadataHash)`, but **the input schema in §3.2 has no `metadataHash` field**, and no note says how it is computed.
- **Options:** (a) the script computes it, e.g. `keccak256` of a canonical encoding of `{description, valuationBasis, custodianId}`; (b) a new input field supplied by the provider; (c) a hash of an off-chain document (IPFS CID / PDF) referenced by a new field.
- **Coder's provisional choice:** none. The schema has no such field, because inventing one would be deciding behaviour.
- **Recommendation:** (a), with the canonical encoding written down in the maths note. Then the schema stays unchanged and the hash is reproducible by a third party.
- **Blocks:** T0.6 (`register` signature), T6.1a step 2. **If (b) or (c), the schema changes.**

### A3. How does `custodianId` map to the custodian key on-chain?
- **Research says:** `"custodianId": "custodian-brinks-dxb"` is an input field, and `BadAttestationSig` checks against "the registered custodian key". It doesn't say where the id → key binding lives or whether `register` takes it.
- **Options:** (a) `register` takes a custodian id (or address) and the registry stores it per asset; (b) one global custodian for MS1, so `custodianId` is informational only; (c) the custodian is fixed at wiring time (T5.1).
- **Coder's provisional choice:** the field is validated as a non-empty string only.
- **Blocks:** T0.6, T4.4, and whether the field is used on-chain or is just a label.

## Part B — Gaps in the schema itself (no T0.6 dependency)

### B1. Which `valuationTs` is authoritative: the input file's or the envelope's?
- **Research says:** the input has `valuationBasis.valuationTs`, and the signed envelope also carries `(reserve, seq, valuationTs)` (§4.2 step 2). `ValuationStale` is checked on-chain, so presumably against the **envelope's**.
- **Risk:** two timestamps that can disagree. An operator may edit the input file and expect it to fix a `ValuationStale` revert, but it won't.
- **Question:** should the input field be (a) removed, (b) kept as informational, or (c) required to equal the envelope's, with the script aborting on mismatch?
- **Coder's provisional choice:** kept, validated as a positive integer of Unix seconds.

### B2. What is `unitValue` used for?
- **Research says:** `unitValue` is in §3.2, but nothing in flow A (§3.3) reads it. Admission compares **reserve vs supply**, not value.
- **Question:** is it (a) informational for the receipt/console, (b) an input to `metadataHash` (ties to A2), or (c) to be removed?
- **Coder's provisional choice:** kept, validated as a positive base-10 integer string.

### B3. `assetId` format
- **Research says:** only the example `gold-lot-001`.
- **Coder's provisional choice:** `^[a-z0-9][a-z0-9-]{0,31}$`, lowercase slug of at most 32 chars.
- **Question:** confirm, or give the rule. Note this ties to A1.

### B4. `attestor` values
- **Research says:** `"attestor": "custodian"`. Q11 (insurer as co-signer) is still open.
- **Coder's provisional choice:** only `"custodian"` is accepted. Widening to `"insurer"` is a one-line change in the type and the schema.
- **Question:** keep it custodian-only until Q11 is answered, or add `"insurer"` now?

### B5. Address checksums
- **Coder's provisional choice:** format only (`0x` + 40 hex). EIP-55 checksum isn't checked, because that needs keccak, i.e. a runtime dependency in a package that is meant to have none.
- **Question:** is format-only acceptable for the shared validator, with viem/the script catching bad checksums? Or should checksum validation be a requirement?

### B6. `attestations[].path` base directory
- **Coder's provisional choice:** documented as relative to `contracts/`, matching §3.2's `script/input/...`.
- **Question:** confirm. T6.1b uploads the envelope rather than reading a path, so should the page ignore `path`, or should the field become a union (path | inline bytes)?
