# 🐞 T6.0 — Debugger Brief

**For the [[Debugger Agent]].** T6.0 is built and its tests are green ([[T6 - Provider Onboarding Console#11. Coder handoff — T6.0 (2026-10-27)|§11]]), and the nine open questions are answered ([[T6.0 - Researcher Answers]]). Green tests are not the bar — **the bar is that nothing bad gets through**. This note is the list of everything that must be tried.

---

## 0. What you are actually doing, in reality

Remember the scene. A provider is onboarding a gold bar. Somewhere between his typing and the blockchain sits **one JSON file**, and this validator is the only thing that reads it before real transactions are broadcast and real tokens are minted.

So picture the file wrong in every way a file can be wrong — a number where a string belongs, a negative supply, an address with a character missing, a stray `"privateKey"` someone pasted in, the same field twice, a thousand attestations. **For each one, either the validator catches it and says something a human can act on, or it slides through and surfaces later as a failed broadcast, a stranded PENDING asset, or — worst case — a key committed to git.**

Your job is not to make tests pass. It is to **try to get something bad past the gate**, and when you do, hand the Coder a reproducible case.

**Important: this validator is a convenience, not a security boundary.** The real enforcement is on-chain. A bug here means a bad developer experience and a possible leaked secret — not a stolen token. Severity judgements below follow that.

## 2. The attack surface, in five groups

### Group A — JSON-level tricks (before any field is looked at)

| # | Try this | Expected |
| - | -------- | -------- |
| A1 | `null` as the whole input | One issue at path `""`. **Never a thrown exception.** |
| A2 | An array as the whole input | One issue at `""` |
| A3 | A string, a number, `true` as the whole input | One issue at `""` |
| A4 | `undefined` / no argument | One issue at `""`, no crash |
| A5 | **Duplicate keys** — `{"assetId":"a","assetId":"b"}` | `JSON.parse` keeps the last; document that the validator cannot see this, and that **git review is the only defence**. Not a bug — but if undocumented, it is a doc defect. |
| A6 | `__proto__`, `constructor`, `prototype` as keys | Rejected as unknown properties; **no prototype pollution** — assert `({}).polluted === undefined` after |
| A7 | 10 MB of nested junk in an unknown field | Rejected, and returns in reasonable time (no catastrophic regex) |
| A8 | A BOM or trailing newline in the file | Parses; not the validator's concern, but confirm the script's `vm.parseJson` tolerates it |

**A6 is the one that matters.** A validator that walks arbitrary object keys and then builds an object is where prototype pollution lives. Verify it explicitly.

### Group B — field-level edge cases

| # | Try this | Expected |
| - | -------- | -------- |
| B1 | `assetId: ""` | Rejected, path `/assetId` |
| B2 | `assetId` 33 chars | Rejected |
| B3 | `assetId: "Gold-Lot-001"` (uppercase) | Rejected — B3 of the answers note |
| B4 | `assetId: "-gold"` / `"gold-"` / `"go--ld"` | First rejected (leading `-`); confirm the latter two against the stated regex and **document the verdict** either way |
| B5 | `assetId` with Unicode that looks ASCII (`gоld` with Cyrillic о) | Rejected by the regex. Confirm — this is a real id-spoofing vector once ids become keccak hashes |
| B6 | `description: ""` | Decide and document: currently non-empty required? If it feeds `metadataHash` (A2), an empty description is legal but useless. **Research question if unclear.** |
| B7 | `intendedSupply: "0"` | Rejected, > 0 |
| B8 | `intendedSupply: "007"` | Rejected, no leading zeros |
| B9 | `intendedSupply: "-5"`, `"1e18"`, `"0x10"`, `" 1"`, `"1 "`, `"1_000"` | All rejected |
| B10 | `intendedSupply` = 78 digits (> `uint256` max) | **Likely gap.** Expected: rejected with "exceeds uint256". If it passes, it fails on-chain as an unreadable revert — exactly what §3.4 exists to prevent |
| B11 | `unitValue: "0"` | Rejected |
| B12 | `valuationTs: 0`, `-1`, `1.5`, `1e20`, `NaN` as JSON | All rejected |
| B13 | `valuationTs` far in the **future** (year 2100) | **Likely gap.** A future valuation passes clause 4 trivially (`now − ts ≤ τ` with a negative left side). Expected: rejected, or at minimum a loud warning. **This is the highest-value item in this brief.** |
| B14 | `currency: "usd"` / `"US"` / `"USDT"` | Decide: ISO 4217 is 3 uppercase letters. Confirm the rule and that it is enforced |
| B15 | `treasuryWallet: "0x0000...0000"` | **Likely gap.** The zero address is format-valid. Expected: rejected — minting to zero burns the supply |
| B16 | `treasuryWallet == token` | Rejected or warned: a token minting to itself is always a mistake |
| B17 | Address 39 or 41 hex chars; `0X` prefix; no prefix; mixed-case failing EIP-55 | First three rejected; the last is **AC-20** — format-only here, enforced in the script and console |
| B18 | `custodianId: ""` | Rejected |

### Group C — the `attestations` array (and B6's new union)

| # | Try this | Expected |
| - | -------- | -------- |
| C1 | `{ attestor, path, bytesBase64 }` — both members | Rejected, "exactly one of path or bytesBase64" |
| C2 | `{ attestor }` — neither member | Rejected, same message |
| C3 | `path: ""` | Rejected |
| C4 | `path: "../../../etc/passwd"` or `"/etc/passwd"` or `"C:\\keys"` | **Path traversal. Likely gap.** The path is read by `vm.readFile` relative to `contracts/`. Expected: reject anything absolute or containing `..`. Severity is low (local, operator-supplied) but it is free to close and an examiner will look for it |
| C5 | `bytesBase64: "not base64!"` | Rejected |
| C6 | `bytesBase64: ""` | Rejected |
| C7 | 1,000 entries | Accepted by the type (the "exactly one for MS1" rule is T6.1a's). Confirm no quadratic blow-up in issue collection |
| C8 | Two entries both `attestor: "custodian"` | Accepted here; T6.1a rejects. Confirm the brief's division of labour holds |
| C9 | `attestor: "insurer"` | Rejected — B4; Q11 is undecided |
| C10 | `attestor: "CUSTODIAN"` | Rejected (case-sensitive enum) |

### Group D — the TS ↔ JSON Schema pair

The drift test compares field names and required-ness. It does **not** compare everything.

| # | Try this | Expected |
| - | -------- | -------- |
| D1 | For each case in Groups B and C, run it through **both** the TS validator and the JSON Schema (any 2020-12 validator) | **Identical accept/reject.** Any divergence is a real bug: the script and the console would disagree about the same file |
| D2 | Loosen a `pattern` in the JSON Schema only | The drift test should ideally fail. If it does not, note the limit in §11 — patterns and bounds are **not** currently covered by it |
| D3 | Add a field to the schema only, and to the TS only | Drift test fails both ways |

**D1 is the single highest-value exercise in this brief.** A shared contract that two front-ends read differently is worse than no shared contract, because it looks safe.

### Group E — the error messages themselves

The research treats messages as acceptance criteria, not decoration. So they get tested.

| # | Try this | Expected |
| - | -------- | -------- |
| E1 | Every rejection above | A `path` that points at the actual offending field, JSON-pointer style, including array indices (`/attestations/1/path`) |
| E2 | 6 simultaneous errors | All 6 returned, not just the first (already covered — confirm it holds for the new union) |
| E3 | Read every message aloud as the gold dealer | No type names, no "expected string, got number" where a sentence would do. If a message would not help a provider, it is a defect |
| E4 | A message echoing a rejected value | It must **not** echo the value of a field whose name matched the key-material grep. Rejecting `"privateKey": "0xabc…"` must not print the secret into a log |

**E4 is a genuine secret-leak path** and the one item in this brief with real security weight.

## 3. What to do with what you find

Per [[Agents - Workflow]], route by kind:

| What you found | Where it goes |
| --- | --- |
| It should clearly have been rejected and wasn't (B10, B13, B15, C4, A6, E4) | **Straight to the [[Coder Agent]]** with a failing test — the intended behaviour is in this note, so no research needed |
| TS and JSON Schema disagree (D1) | **Coder**, with the diverging case |
| The research never said (B6's empty description, B4's `go--ld`, B14's currency rule) | **Back to the [[Researcher Agent]]** — do **not** pick a behaviour. Add it to a `T6.0 - Debugger Questions` note the way the Coder did |
| A message is technically right but useless to a provider (E3) | **Coder**, cite AC-5's "operator-facing sentence" rule |
| Only the on-chain layer can catch it | **Not a T6.0 defect.** Note it as a T6.1a/T4.2 requirement so it isn't lost |

**Never widen or narrow the schema yourself to make a case pass.** The schema is the contract between two front-ends; changing it is a Researcher decision.

## 5. The four I expect you to actually find

Stated up front so finding them is confirmation rather than discovery, and *not* finding them means looking harder:

1. **B13 — a future `valuationTs`.** Clause 4 is `now − valuationTs ≤ τ`. A timestamp in 2100 satisfies it with room to spare. Nothing in the research or the schema currently stops it.
2. **B15 — the zero address** as `treasuryWallet`. Format-valid, and a mint to it destroys the supply.
3. **B10 — an amount above `uint256` max.** Passes a "digits only, > 0" check and dies on-chain as a hex blob.
4. **C4 — path traversal** in `attestations[].path`. Low severity, free to close, and the kind of thing a reviewer finds for you.

If all four are already handled, say so in the report — that is a result, not a non-event.
