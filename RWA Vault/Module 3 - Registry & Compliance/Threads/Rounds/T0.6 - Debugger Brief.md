# 🐞 T0.6 — Debugger Brief

**For the [[Debugger Agent]].** T0.6 is **built and Researcher-verified** — AC-T06-1…10 all pass, `forge build` / `fmt --check` / 4 tests green, checked by me and not taken on report. See [[T0.6 - IAssetRegistry Interface]] §16.

So this is **not** a "find the bug that broke the build" brief. It is the opposite, and it is the more dangerous kind.

---

## 0. What you are actually doing, in reality

There is no logic here. Two interface files and a mock whose every function reverts. Nothing computes anything, so nothing can compute it wrongly.

**What can be wrong is the vocabulary itself** — and it is about to be frozen into four other tasks.

Picture what happens next. T2.2 writes a compliance module that calls `isLive`. T6.1a writes a script that calls `admit` and translates `ReserveTooLow` into a sentence for a gold dealer. T6.1b writes a page that decodes `latest()`. T4.1 writes the real contract. All four compile against these two files **starting now**, and all four hard-code these names, these parameter orders and these error selectors.

A name that is merely *awkward* costs nothing. But **three classes of defect here are invisible today and expensive later:**

1. **A selector collision** — two different errors that hash to the same 4 bytes, or an error here that collides with one in `IERC3643`. A script catches the wrong one and tells the provider the wrong thing. Compiles fine. Tests pass.
2. **A parameter order that reads naturally and decodes wrongly** — nothing fails until T6.1b displays a reserve where a sequence number should be.
3. **Natspec that says the wrong caller** — T5.2 assigns roles from this documentation. A doc comment saying `agent` where it should say `owner` becomes a real privilege the multisig didn't intend to delegate.

Your job: **try to make these two files lie.**

## 2. Group A — selector and topic collisions (highest value)

The existing test asserts the 15 error selectors are distinct **from each other**. That is not the real risk.

| # | Try this | Expected |
| - | -------- | -------- |
| A1 | Collect every `error` declared **anywhere** in `contracts/src` and `contracts/test` — `IERC3643`, `IIdentityRegistry`, `IModularCompliance`, `IModule`, the ONCHAINID set — and compute all selectors. Any duplicate across files? | **No collision.** A collision between an `IAssetRegistry` error and an `IERC3643` error is the serious one: both are in the call path of a single `mint`, so T6.1a's translation table could attribute a failure to the wrong contract and print a confidently wrong sentence |
| A2 | Same for **event topic0** across all interfaces | No duplicate signature hash |
| A3 | Check each error against the 4-byte selectors of common OpenZeppelin / forge-std errors reachable in the same call (`ERC20InsufficientBalance`, `OwnableUnauthorizedAccount`, `Panic`, `Error(string)`) | No collision |
| A4 | `AssetNotLive(bytes32, AssetState)` — does the enum encode as `uint8` in the selector string? Confirm the selector is computed over `AssetNotLive(bytes32,uint8)` and that `cast 4byte-decode` round-trips it | Round-trips; **if it does not, T6.1a cannot decode it**, which breaks AC-5 |
| A5 | Are any two errors distinguishable only by parameter *names* rather than types? e.g. a future `ReserveTooLow(uint256,uint256)` vs something else with two words | Flag any pair where a decoder could mis-attribute |

**A4 is the one I would bet on.** Custom errors carrying an `enum` parameter are a known source of decode surprises, and `AssetNotLive` is the error T2.2's veto will surface most often.

## 5. Group D — is it implementable *correctly*, not just at all

The mock proves the interface **compiles**. It does not prove the interface is **sufficient**.

| # | Try this | Expected |
| - | -------- | -------- |
| D1 | Sketch (do not finish) a real `AssetRegistry` satisfying §2's six transitions. Is any function or piece of state missing from the interface? | Every transition expressible. **Report anything missing — that is a research gap, not a bug** |
| D2 | Can `admit` enforce clause 3 using only interface members? It needs reserve (`latest`), supply (`tokenOf` → `totalSupply`) and τ (`valuationWindowOf`) | All reachable. If `tokenOf` is unset, `TokenNotBound` exists |
| D3 | Can `AssetLiveModule` (T2.2) enforce `totalSupply + amount ≤ reserveOf` with only `isLive` and `reserveOf`? | Yes. If not, the invariant has nowhere to live — **escalate immediately**, this is the one that matters |
| D4 | Does anything require enumerating assets? | It must not. There is deliberately no `getAllAssets()` (§9.1) |
| D5 | Under Q14=B, can the registry express "accept lower reserve, block mints"? | `UnderReserve` event + module veto. Confirm no extra interface member is needed |

**D3 is the question this whole brief exists for.** The invariant `attestedSupply ≤ reserve` moved out of the registry and into the compliance module (ADR `0014`). If the interface cannot support that enforcement, the protocol's one safety property has no home, and we find out in T2.2 instead of now.

## 6. What to do with what you find

| What you found | Where it goes |
| --- | --- |
| A selector or topic collision (Group A) | **Me, immediately.** Fixing it means renaming a frozen name — Researcher decision, and it cascades into T6's §3.4 table |
| Natspec names the wrong caller (C1–C3) | **[[Coder Agent]]** directly — the intended caller is in §3 and ADR `0019`, so no research needed |
| A stale reference to a removed member (C6) | **Coder** directly |
| A decode failure (Group B) | **Me** if it needs a type or order change; **Coder** if the natspec is merely wrong |
| The interface cannot express a required behaviour (D1, D3, D5) | **Me.** This is a research gap. Do **not** add a function to make it work |

**Never add, rename or retype a member yourself.** AC-T06-2 freezes every name precisely because four tasks are about to depend on them. A rename is cheap today and expensive the moment T2.2 compiles.
