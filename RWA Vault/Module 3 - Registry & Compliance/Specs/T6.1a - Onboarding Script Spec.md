# 🧭 T6.1a — The onboarding command: build spec

**For the [[Coder Agent]].** This is the current form of [[Specs/T6 - Provider Onboarding Console]] §3, updated for what
was built and ruled after it was written. **Where the two differ, this note wins.** The T6 spec's AC numbers are kept,
and where a criterion changed it says so. Also in this batch: `VerifyWallet.s.sol` ([[Specs/T5.1 - Deploy Script Spec|T5.1 §7]],
AC-T5-6/7), which T6.2 S4 needs.

## 0. What changed since the T6 spec was written

| T6 spec said | Now | Why |
| ------------ | --- | --- |
| The script reads and decodes a CBOR envelope | **There is no envelope codec yet** (M2 `envelope-codec` is a 38-line type stub, and M2 T3 is not built). Clause 1 runs off-chain under ADR 0027 | §2 defines an **interim MS1 fixture attestation** and a verifier step |
| "verify via `pqctl`" (ADR 0027) | **`pqctl` cannot verify ML-DSA-65.** It is the offline SLH-DSA root ceremony tool, with its algorithm hard-coded to SLH-DSA-SHA2-128s (`packages/pq-core/native/pqctl/src/main.rs:13`) | The verifier step calls `@rwa-vault/pq-core`'s ML-DSA-65 `verify` (napi) instead. ADR 0027's "or `pqctl`" wording is recorded as inaccurate, see §8 |
| Asset binding happens at wiring time (T5.1) | `register` and the owner's `setTokenFor` happen **here** | T5.1 spec §3 |
| `admit(env, intendedSupply)` | `submitAttestation(att, envelopeHash)` on the source, then `admit(assetId, intendedSupply)` | Built T4.3, ADR 0017 / 0027 |
| AC-17 third test: transfer of a non-LIVE asset reverts | That transfer **succeeds**. The test is about a mint | ADR 0019 §6 (T3 spec §10, applies to T6.3) |

## 1. One command, two stages

```
pnpm m3:onboard <input.json> [--broadcast]
  stage 1 (Node, off-chain): validate input → verify the custodian attestation (clause 1) → write .onboard/<slug>.verified.json
  stage 2 (forge script):    contracts/script/OnboardAsset.s.sol reads the input + the verified file + deployments/<chainid>.json
```

A root `package.json` script runs `node scripts/onboard/run.mjs`. That script does stage 1, then spawns
`forge script script/OnboardAsset.s.sol --rpc-url $M3_RPC_URL [--broadcast]` with
`ONBOARD_INPUT` and `ONBOARD_VERIFIED` set. **No `--ffi`:** the forge script never runs a subprocess. Without
`--broadcast` the whole thing is a dry run (T6.2 S6). Keys come only from `M3_AGENT_PK` / `M3_OWNER_PK` (owner only on
anvil), never from the input (T6.0 AC-3).

## 2. Stage 1 — validation and clause 1 (off-chain, ADR 0027)

**2.1 Validate** with `validateOnboardingInput` from `@rwa-vault/types` (the T6.0 validator, so the console and the
script can never disagree on input). On failure, print every issue as `<json pointer>: <message>` and exit 1.

**2.2 Interim MS1 fixture attestation format** (`*.att.json`, referenced by `attestations[0].path`). It is replaced
behind the same seam when M2 ships its codec:

```jsonc
{
  "format": "rwa-vault/ms1-fixture-attestation@0",
  "algorithm": "ML-DSA-65",
  "chainId": 31337,
  "assetRef": "gold-lot-002",
  "reserve": "999900000000000000000",   // fine grams × 1e18 (ADR 0020), base-10 string
  "seq": 1,
  "valuationTs": 1761600000,
  "signature": "<base64>"
}
```

**Signed message:** `abi.encode(string format, uint256 chainId, bytes32 assetId, uint256 reserve, uint64 seq, uint64 valuationTs)`
with `assetId = keccak256(bytes(assetRef))`. `chainId` is signed so a devnet envelope can never be replayed onto a
testnet.

**The custodian's public key is NOT in the envelope.** It is read from `contracts/script/input/custodian.mldsa65.pub`
(committed), and its `keccak256` must equal `custodianKeyHash` in `contracts/script/input/custodian.json`. A key
inside the envelope would let anyone sign for themselves.

**2.3 Verify, then write the verified file.** Run pq-core ML-DSA-65 `verify(pub, message, signature)`.
- On failure, exit 3 and print the T6 §3.4 sentence for **`BadAttestationSig`**: *"The custodian's signature on
  this attestation is not valid for the registered custodian key."* This is where that error lives in MS1. It is never
  raised on-chain.
- `chainId` ≠ the RPC's chain → exit 3, `AttestationForOtherChain(expected, got)`.
- `assetRef` ≠ input `assetId` → exit 3, `AttestationForOtherAsset(input, envelope)`.

On success it writes `.onboard/<slug>.verified.json` (gitignored):
`{ assetId, reserve, seq, valuationTs, envelopeHash, verifiedAt, verifier: "pq-core ml-dsa-65 <version>" }`, where
`envelopeHash = keccak256(raw file bytes)` (opaque to the contract, T4.3; M2 T3.8 replaces the recipe).

**2.4 Fixture generator** `scripts/onboard/make-fixture-attestation.mjs --asset <slug> --reserve <wei> --seq <n> --ts <unix|now|stale>`.
It is devnet only: it refuses unless the chain id is 31337. It generates or reuses a keypair under `.onboard/keys/`
(gitignored) and writes `custodian.mldsa65.pub`, `custodian.json` and the `.att.json`. T6.2's prepared envelopes A
(fresh) and B (`--ts stale`) come from this.

## 3. Stage 2 — `OnboardAsset.s.sol`

Reads `deployments/<chainid>.json` for every address and nothing else. Steps, with on-chain state read before each
one so that **any re-run continues instead of failing** (AC-6):

**P — pre-flight. No transaction is sent if any of these fail** (AC-7, AC-21):
1. Exactly one attestation (`TooManyAttestationsForMs1(count)`, T6 spec §7).
2. EIP-55: every mixed-case address in the input equals `vm.toString(addr)`; all-lowercase is accepted
   (`BadChecksumAddress(field, given)`, AC-20).
3. `valuationBasis.source` starts with `FIXTURE` and `block.chainid != 31337` → `FixtureSourceOutsideTest(source)`
   (AC-22). "Test" means anvil. T6.2 runs on anvil, so it is allowed there.
4. `intendedSupply == grossWeight × fineness / 10000` exactly, else `SupplyWeightMismatch(intended, derived)` (the
   fineness-as-a-field promise from T6 spec §9.0).
5. `input.token == deployments.token`, else `TokenMismatch(input, deployed)`.
6. `identityRegistry.isVerified(providerWallet)`, else stop with *"The provider wallet <addr> is not KYC-verified.
   Run VerifyWallet first (How to Run §6)."* (`ProviderNotVerified(wallet)`, AC-7).
7. Print the input's `valuationTs` beside the verified file's. If they differ by more than 1 hour, warn (AC-19).

**S — state branch:**

| `stateOf(assetId)` | Do |
| ------------------ | -- |
| UNREGISTERED | `register(assetId, metadataHash, slug)` (agent), then continue |
| PENDING | continue |
| LIVE, `totalSupply == 0` | skip to **M** (a run that stopped after admit, before mint) |
| LIVE, `totalSupply == intendedSupply` | print "already live" and the receipt, then exit 0. **No second mint** (AC-6) |
| LIVE, any other supply | stop: `PartialSupply(onChain, intended)`. A human decides |
| FROZEN | stop: *"This asset is frozen; an operator must resolve it."* (`AssetIsFrozen`). Never auto-unfreeze |

**`metadataHash`: the canonical recipe, final.** It is the eight `METADATA_HASH_FIELDS` in order. This replaces the
six-field form of [[T6.0 - Researcher Answers]] A2, which predates `grossWeight` and `fineness`:

```solidity
keccak256(abi.encode(
    string  assetId,          // the slug
    string  description,
    uint256 grossWeight,      // parsed from the base-10 string
    uint16  fineness,
    string  valuationBasis.source,
    string  valuationBasis.currency,
    uint256 valuationBasis.unitValue,
    string  custodianId
))
```

T6.1b computes the same thing with viem `encodeAbiParameters`. A shared golden vector goes in
`packages/types/src/__tests__/fixtures.ts` (input → hash), and both the Solidity test and a TS test assert it.

**B — binding.** If `tokenOf(assetId) == 0`: on anvil with `M3_OWNER_PK` set, send `setTokenFor(assetId, token)` as
the owner. Otherwise print `to / data` for the multisig and **exit 2** with *"Waiting for the owner multisig to bind
the token. Re-run this command after it confirms."* (a named pause in T6.2). If `tokenOf` returns a different token,
stop with `TokenAlreadyBoundElsewhere`.

**A — attest and admit.**
1. Read `source.latest(assetId)`. If its seq is below the verified seq, `submitAttestation(att, envelopeHash)`
   (agent as submitter). If it equals the verified seq and `envelopeHashOf == envelopeHash`, skip (idempotent).
   Otherwise stop with *"The source already holds a newer attestation (seq M)."*
2. If PENDING, run the clause 2–4 pre-check off-chain and **name the failing clause before sending**. Then
   `try registry.admit(assetId, intendedSupply)`. On a revert, decode the selector to the §3.4 sentence (AC-5). The
   four sentences stay as in the T6 spec. `ValuationStale` adds *"…This is the timestamp inside the signed envelope;
   editing the input file will not change it."* (AC-19). `ValuationInFuture` gets its own sentence. An unknown
   selector prints the raw hex **and** says "unexpected; report it".

**M — mint.** Pre-flight (AC-21): `isLive`, freshness (`valuationTsOf` + window), and
`totalSupply + intendedSupply ≤ reserveOf`. Name the failing condition, then `token.mint(providerWallet,
intendedSupply)` (agent). A `TransferNotCompliant` that still happens is printed as *"Compliance refused the mint;
the pre-flight passed, so the state changed between the check and the send. Re-run."*

**R — receipt** (AC-23): state, `reserveOf`, `totalSupply`, seq, `valuationTs`, token, provider balance, every tx
hash, the envelope hash, and the line `units: intendedSupply and reserve in FINE grams × 1e18; unitValue per FINE
gram (ADR 0020)`. On a FIXTURE lot also print `MS1 FIXTURE ATTESTATION — NOT INDEPENDENTLY VERIFIED` (ADR 0017).

**The script never** deploys, transfers, forced-transfers, freezes a wallet or pauses (T6 §3.5, §4.4).

## 6. For the Debugger — intended behaviour

| Case | Intended |
| ---- | -------- |
| Input edited after a successful run (same slug, new description) | `register` is skipped because the asset is not UNREGISTERED. The receipt prints *"metadata on chain differs from this input"* when `metadataHashOf` ≠ the recomputed hash, and exits 0 without changing anything |
| Envelope reserve > intended supply | allowed (the invariant is ≤, T6 spec §7) |
| Dry run on a LIVE asset | prints the receipt, sends nothing |
| Anything not here | ASK the Researcher |

## 7. Out of scope here

T6.3 (bypass test) and T6.1b (console) follow in that order (Q19). The real M2 envelope replaces §2.2 behind the same
two seams (the verified file and `IReserveAttestationSource`). T4.4 is ticked when §2.3 is verified.

## 8. Recorded inaccuracy (no decision needed)

ADR 0027 says clause 1 is checked by "the M2 verifier — or, until it exists, M1's native ML-DSA-65 verify via
`pqctl`". `pqctl` is SLH-DSA-only. The M1 ML-DSA-65 verify is reached through `@rwa-vault/pq-core` instead. The
decision itself (verify off-chain with M1 code) is unchanged, so this is a wording fix, logged in the ADR Index notes
rather than a superseding ADR.
