# T0.7 — `IReserveAttestationSource` Specification

Settles the seven points in [[Thread - T0.7 Reserve Attestation Source]]. **Specification only — no code written.** The Coder plan and acceptance criteria are handed off in that thread.

> ## The headline finding
> **The shared interface does not change.** Not one signature, name or type. The custody session asked me to weigh whether points 2 and 3 would force an interface change — under ADR `0025` that would mean a redeploy — and the answer is no, for two different reasons: point 3 is **Phase 2, not MS1** (Q17 = B), and point 2 changes **what the comment says, not what the code is**. What grows is the MS1 *implementation*, which is not this interface.

---

## 0. What this seam is, in reality

A bar of gold sits in a vault in Dubai. A contract on a blockchain cannot see it, weigh it, or phone the vault. It can only ever be *told*.

**This interface is the mouth through which it is told** — and the only one. Everything downstream, the whole claim that a token is backed, reduces to two questions the interface answers: *how much fine gold does someone accountable say is in there*, and *when did they say it*.

Two things make the seam worth its own specification rather than a comment:

1. **It is the one M3 interface that someone outside these conversations must implement exactly.** For MS1 we write both sides. In Phase 2, M5's oracle replaces our implementation — written weeks later, by whoever owns M5, which today is nobody (M5 is 0%). If the contract between the two sides lives only in our heads, the swap ADR `0017` promises is a wish.
2. **It is where the chain stops being able to check anything.** `admit`'s clauses 2–4 are arithmetic the contract performs itself. Clause 1 — is this really the custodian's signature — is now evaluated **off-chain** (ADR `0027`). Past this seam, the protocol is trusting a process rather than verifying a computation, and a specification is the only place that can be said honestly.

## 1. The submit path (thread point 1)

`submitAttestation` is **deliberately absent from the shared interface** and stays absent. M5 has no envelope to submit; a shared function it must accept and ignore would be the dead-parameter smell already rejected once in T0.6 §6.

It belongs to the **MS1 implementation** (`ReserveAttestationSourceMS1`), and this is its specification.

### 1.1 Signature

```solidity
function submitAttestation(
    bytes32 assetId,
    uint256 reserve,       // fine grams x 10^18 (ADR 0020)
    uint64  seq,
    uint64  valuationTs,
    bytes32 envelopeHash   // keccak256 of the ML-DSA-65 envelope bytes (ADR 0027)
) external;
```

**It takes decoded fields plus a hash, not the envelope bytes.** Under ADR `0027` the contract no longer verifies anything about the envelope, so accepting raw bytes would be theatre: it would look like the chain was checking a signature while storing an opaque blob it never reads. Passing the hash states the honest thing — *this is the document the off-chain check was performed against, go and re-verify it yourself.*

### 1.2 Who may call it

The **allow-listed Tier 1 service key** (ADR `0015`, ADR `0027`), held by the operator — not the `owner` multisig, which would make every attestation a governance event, and not the custodian, who signs the envelope but never holds a key on our chain.

```solidity
function isSubmitter(address) external view returns (bool);
function addSubmitter(address) external;      // owner
function removeSubmitter(address) external;   // owner
error NotAuthorisedSubmitter(address caller);
```

Same shape as `IAssetRegistry`'s agent set, and for the same reason given there: two roles do not need a role framework, and OpenZeppelin's `AccessControlUnauthorizedAccount` is absent from [[T6 - Provider Onboarding Console]] §3.4's translation table, so it would print a hex selector at an operator.

### 1.3 Validation on submit, and its errors

```solidity
error StaleSequenceAtSource(uint64 submitted, uint64 lastAccepted);
error ValuationInFuture(uint64 valuationTs, uint64 blockTime);
error EmptyEnvelopeHash();
error EmptyAssetId();
```

`reserve == 0` is **accepted**. A custodian legitimately attesting an empty vault is information, not an error, and refusing it would leave the chain showing the last non-zero figure — the same mistake ADR `0019` decision 3 rejected for the under-reserve case.

### 1.4 The event — this is the part M9 anchors

```solidity
event AttestationSubmitted(
    bytes32 indexed assetId,
    uint256 reserve,
    uint64  seq,
    uint64  valuationTs,
    bytes32 envelopeHash,
    address submitter
);
```

**This event is the audit trail that makes ADR `0027` defensible.** Off-chain verification is only honest if a third party can repeat it, and repeating it requires knowing *which* document was checked, *what* was claimed from it, and *who* claimed it. All three are in this event and nowhere else. If it is dropped or trimmed, clause 1 becomes an assertion with no trail.

## 2. ADR 0027 absorbed — the header on disk is now wrong (thread point 2)

**On disk now**, `IReserveAttestationSource.sol:8-11`:

> *"Signature verification (admission clause 1) therefore happens on the source at submit time; the registry checks clauses 2-4 at `admit`."*

ADR `0027` postdates that sentence and reverses its first half. **Clause 1 is evaluated off-chain for MS1** — by the M2 verifier, or `pqctl` using M1's native ML-DSA-65 verify until M2 exists. The source records what an allow-listed submitter asserts, and anchors the hash so the assertion can be re-checked by anyone.

The sentence must be replaced, not softened. A comment that says the contract verifies a signature it does not verify is worse than no comment: it is the exact claim an examiner will test first.

**Replacement wording** (NatSpec, no signature change):

> For MS1, admission clause 1 is verified **off-chain** (ADR `0027`): the M2 verifier — or `pqctl` with M1's ML-DSA-65 verify until M2 exists — checks the custodian envelope, and an allow-listed Tier 1 submitter then records the decoded fields plus the envelope hash via the implementation's own `submitAttestation`. **This contract verifies no signature.** M9 anchors the hash, so anyone may fetch the original envelope and re-verify it offline against the custodian's registered key. The registry checks clauses 2–4 at `admit`.

### 2.1 `BadAttestationSig` — kept, re-documented, and this is a researcher ruling

Under ADR `0027` nothing on-chain can raise it in MS1. **Keep it declared**, and document it as *raised by the off-chain verifier's reporting path, and reserved for a Phase 2 implementation that verifies on-chain.*

Removing it would break [[T6 - Provider Onboarding Console]] §3.4's translation table — which maps it to the operator sentence *"The custodian's signature on this attestation is not valid for the registered custodian key"* — and would have to be re-added in Phase 2. The sentence is still exactly what an operator needs to read when the **off-chain** check fails; only the thing that raises it moved. Deleting a correct message because the mechanism moved would be churn.

**But it must not be left reading as if the contract raises it**, which is what it says today. That is the honest half of this ruling, and the one that matters.

## 3. The insurer is Phase 2 — the interface does not grow now (thread point 3)

**The thread's point 3 overstates MS1, and the Coder flagged the same thing.** It reads Q11 = B as putting the insurer 2-of-2 and the fifth clause at the source on submit. **Q17 = B supersedes Q11's timing**: four clauses, one custodian signer for MS1; the insurer 2-of-2 and the policy clause come in Phase 2 under their own ADR.

Quoting `Questions/Q17 …` frontmatter on disk:

> `decision: "B — 4 clauses, one custodian signer for MS1; insurer 2-of-2 + policy clause in Phase 2 under its own ADR"`

So **no second signer, no `policyCoverage`, no `policyExpiry`, no attestor registry, and no fifth clause** in the struct, the errors or the predicate today. Q11 remains the target design; Q17 settles only when.

This is the answer to the custody session's first question. Under ADR `0025` there are no proxies, so an interface change after deployment is a redeploy — and Q17 = B means there is no such change to make.

### 3.1 What Phase 2 adds, and why it stays additive

| Phase 2 needs | Where it lands | Why it is additive |
| --- | --- | --- |
| A second signature | The **envelope** and the off-chain verifier | The envelope schema is M2's; this interface never sees a signature |
| `policyCoverage`, `policyExpiry` | A **new** struct member set, or a second view | Adding members to a returned struct is a new interface version for M5 to implement, not a change to MS1's deployed one |
| Clause 5 | `AssetRegistry.admit` | Predicate change, T4.2's business |
| An attestor set, m-of-n | The Phase 2 **implementation** | Same seam, different implementation — which is ADR `0017`'s whole point |

The T6.0 schema's `attestations` array already makes the provider-side addition additive. That was decided on exactly this reasoning and it has now paid off twice.

## 4. Replay and monotonicity at the source (thread point 4)

**Ruling: the source MUST reject a non-increasing `seq` on submit, with `StaleSequenceAtSource`. The registry's clause-2 check at `admit` stays.** Two gates, different jobs.

The weak argument for this is defence in depth. The real argument is that **`latest()` is read between submit and admit, and nothing else protects it.**

`admit` checks clause 2 against `lastSequenceOf` in the *registry*. But submit and admit are separate transactions, and admit may be delayed or never happen. In that window, `latest()` is the authority — [[T6 - Provider Onboarding Console]]'s console reads it in pre-flight to render its checks, and the operator reads those. With no source-side monotonicity, replaying an older envelope would **overwrite a newer attestation**: the console would show a stale reserve and an older `valuationTs`, and clause 4 might then reject an asset whose current attestation was fine. The chain would not be wrong; the *record* would be, which is the thing a provider is looking at.

Put plainly: the registry's check protects **admission**. The source's check protects **its own stored state**, which other things read. Neither substitutes for the other.

**Equal `seq` is rejected too** — strictly increasing, not non-decreasing. An identical re-submission is either a replay or a mistake, and accepting it would let the same `seq` carry a different `reserve`.

## 4.1 `seq` is NOT M2's envelope nonce — ruled 2026-10-28

Raised by the custody session as the M2-side consumer review §8 said was missing, and it is a sharper finding than the
width question I had logged.

**On disk now**, `packages/envelope-codec/src/index.ts:32`:

```ts
/** Same-signer replay protection; strictly incrementing per signer and action. */
nonce: bigint;
```

Two problems, and the second is the one that matters.

**The width is not merely wider — it is unspecified.** `bigint` is arbitrary precision, and a grep across
`packages/envelope-codec` finds no cap, no width constraint and no validation. So `uint64 seq` is not at risk of
mismatching a *declared* width; it is at risk of mismatching **no declared width**, which is worse, because nothing on
the M2 side will ever fail a test. Truncation would surface the first time a real nonce exceeded 2⁶⁴−1.

**The two counters count different things.** M2's nonce is *per signer and action*. Clause 2's `seq` is **per asset**.
If one custodian attests for two lots, a per-signer nonce advances across both — so lot A's `seq` would jump whenever
lot B was attested. That does not break clause 2, since the value still only increases for A, but it makes gaps normal,
leaks one asset's activity into another's sequence, and falsifies the obvious reading that `seq` counts attestations
for *that* asset. Worse, two custodians attesting the same asset over its life would contribute from independent nonce
spaces, so the numbers would not be comparable across a custodian change.

**Ruling: `seq` is a per-asset counter and is NOT the envelope nonce.** The spec says so explicitly, because the word
"sequence" invites exactly the wrong wiring, and wiring the nonce straight in is a one-line change someone will make
unless told not to.

- `seq` is supplied by the submitter and must reflect **the custodian's own ordering of attestations for that asset**.
- The envelope `nonce` remains M2's replay protection **for the envelope**, off-chain, and never reaches this contract.
- The source enforces strict increase (§4) — that is what makes a submitter-supplied number safe.
- **`seq ≥ 1`. Zero is not a legal first attestation** — added 2026-10-29 from the Debugger's ASK. The registry's clause 2
  is `seq > lastSequenceOf`, and `lastSequenceOf == 0` is how the registry says *never admitted*. So a `seq` of 0 is
  indistinguishable from absence: the asset reports `hasAttestation == true` and **can never be admitted**, sitting in
  PENDING permanently with no error explaining why. The general rule is that **a counter whose zero value doubles as
  "unset" must start at 1.** Giving the registry a separate admitted-flag so `seq = 0` could be legal was considered and
  rejected — more machinery to make a sentinel usable, for no gain. `error InvalidSequence(uint64 seq)` belongs to T4.4.
- **The source MUST reject an equal `seq` even when `valuationTs` moves** — the "heartbeat" case. A source that accepts
  the same `seq` with a fresher timestamp lets an **old reserve acquire a new valuation date with nothing newly
  attested**, so clause 4 keeps passing forever and ADR `0021`'s staleness protection is defeated by a source that only
  ever says "still fine". Found by mutation: a conformance suite whose probes reuse one timestamp cannot see it.
- **Additionally: the source MUST reject a repeated `envelopeHash`,** with `error EnvelopeAlreadySubmitted(bytes32)`.
  This closes exact replay independently of `seq`, and ties replay protection to **the document** rather than to a
  number an operator types. The two guards fail differently, which is the point.

**Why not have the source assign `seq` itself** (`lastSeq + 1`), which would make replay impossible by construction? I
considered it and rejected it. A source-assigned counter carries no information from the custodian, so it cannot detect
**out-of-order submission**: two envelopes signed A then B, submitted B then A, would both be accepted and the older
valuation would end up as `latest()`. Clause 4 catches a *stale* valuation but not an out-of-order pair inside the
window. A submitter-supplied `seq` derived from the custodian's ordering rejects A. Keeping it is the stronger property.

**What this costs the operator, stated rather than hidden:** somebody must derive `seq` per asset, and nothing on disk
produces it today. That is an operator procedure T4.4 and T8 must document, and it is now §8's review item.

## 5. The zeroed-struct hazard, as a requirement (thread point 5)

`latest(unknown)` returns an all-zero struct: reserve 0, seq 0, `valuationTs` at the Unix epoch. A caller that skips `hasAttestation` sees an unattested bar as an empty one.

**Ruling: keep the zeroed return — do not revert in `latest()` — and make the guard a stated requirement with tests.**

A reverting view is the wrong fix: `IAssetRegistry.stateOf` deliberately does not revert on an unknown id because T6.1a branches on it, and a source whose view reverts would make every pre-flight read a try/catch. The zeroed return is also what makes the struct cheap to read.

**Three requirements instead:**

1. `hasAttestation(assetId)` MUST be `false` whenever no attestation has been accepted, and MUST become `true` on the first successful submit and never revert to `false`.
2. In the zeroed case, `assetId` MUST be `bytes32(0)` — not the key that was queried. This is the belt: a caller that ignores `hasAttestation` but cross-checks the struct's `assetId` **still fails closed**, because the zero id matches no real asset and the registry reverts `AssetIdMismatch` (ADR `0019` decision 5). The struct's first-member rule already exists for exactly this family of bug; this extends it to the empty case.
3. `AssetRegistry.admit` MUST call `hasAttestation` and revert `NoAttestation(assetId)` before reading `latest`. Already true on disk; this spec makes it a requirement rather than a convention.

Clause 4 incidentally catches this too — an epoch `valuationTs` is wildly stale — but relying on that is relying on a coincidence of ordering. It is an accident that it fails safe, and accidents are not requirements.

## 6. Units, as a requirement (thread point 6)

`reserve` is in **the token's own base units** — for gold, **fine grams × 10¹⁸** (ADR `0020`). Gross weight never appears. The same sentence is now on the interface, `reserveOf` and `admit` after T0.6 §15.

**What a conforming implementation must do when its upstream quotes something else** — and M5's upstream will, because price and weight feeds quote per troy ounce and vaults weigh gross:

1. **Convert at the boundary, before `submitAttestation`.** No unit conversion ever happens inside a contract. Solidity has no fractions, conversion needs a fineness ratio, and an on-chain conversion would bake a rounding policy into an immutable contract (ADR `0025`).
2. **Never store or return the upstream unit.** Not in a second field, not in an event. One unit, or the ambiguity ADR `0020` was amended to kill comes back one layer out.
3. **Round down, toward less reserve.** Where conversion is inexact, the recorded reserve must be the floor. **The justification is the error's direction: rounding down can only ever UNDERSTATE backing, so the error always favours the holder** — the same principle as M4's rounding favouring the pool. Rounding up would overstate backing by the rounding error, and `attestedSupply ≤ reserve` would then hold against a number nobody can produce from the vault. Understating is safe: it refuses a mint that would have been fine. Overstating permits one that is not.
4. **Fail closed on unknown fineness.** If an implementation cannot establish the fineness needed to convert, it must not submit. A guessed fineness is an invented reserve.

## 7. What M5 must satisfy in Phase 2 (thread point 7)

This is the deliverable that matters most, because it is the only part of M3 whose consumer is a stranger.

**Ruling: the conformance requirements ship as an `abstract` test contract, not as prose.** `ReserveAttestationSourceConformance.t.sol`, in the shape of `ERC3643Acceptance.t.sol` (T0.5): abstract, so Forge compiles but skips it, with one `deploySource()` hook. M5 provides a concrete subclass and the suite runs unchanged.

A checklist in a note is something M5's author may never read. A test suite they must subclass is something they cannot avoid — and it is the same device that made the six ERC-3643 guarantees stick.

**The conformance contract:**

| # | Requirement | Test |
| - | --- | --- |
| C1 | `latest(k).assetId == k` for any attested `k` | `test_LatestEchoesKey` |
| C2 | `latest(unknown)` is all-zero, **including `assetId == 0`** | `test_UnknownAssetReturnsZeroedStruct` |
| C3 | `hasAttestation` false before, true after, never regresses | `test_HasAttestationIsMonotonic` |
| C4 | `seq` strictly increases per asset across accepted submissions | `test_SequenceStrictlyIncreasesPerAsset` |
| C5 | Neither view ever reverts, for any input | `test_ViewsNeverRevert` |
| C6 | `reserve` is in fine grams × 10¹⁸; no gross or per-ounce value is reachable | `test_ReserveUnitIsFineGrams` (documented + asserted via a fixture) |
| C7 | Per-asset isolation: attesting A never changes `latest(B)` | `test_AssetsAreIsolated` |
| C8 | `valuationTs` is never in the future at the time it was accepted | `test_NoFutureValuation` |
| C9 | No `submitAttestation` is required to conform | satisfied by construction — the abstract suite never calls it |

**C7 is the one that would otherwise be missed**, and it is the failure ADR `0019` decision 5's `AssetIdMismatch` exists to catch from the other side: a source that keys its mapping wrongly hands one bar's reserve to another with every clause passing. C1 and C7 together close it at the source; `AssetIdMismatch` closes it at the registry. Both, because this is the seam where the two halves are written by different people.

## 8. T0.8 is impossible, and what I am asserting without it

The custody session asked me to say this plainly, and it is right to ask.

**T0.8 is "consumer sign-off (M4, M5, M9 owners) on the interfaces". There are no such owners.** From the census on disk: **M2 is at 10%** (skeleton), **M4 is 0%** (not started, queued for Sprint 3), **M5 is 0%** (types scaffolded only). So nobody can sign off on the signatures M5 must later satisfy, because M5 does not exist and has no owner.

**What I am asserting on their behalf, as the Researcher and with no consumer review:**

1. That `latest` + `hasAttestation` is **sufficient** for an oracle-backed implementation — i.e. M5 will never need to push, only to answer. If M5's design turns out to require a push or a subscription, this interface is wrong and ADR `0025` makes it a redeploy.
2. That **fine grams × 10¹⁸** is a unit M5 can produce. Its upstream will quote per ounce and gross; §6 asserts the conversion is M5's job, off-chain, rounding down.
3. **Superseded 2026-10-28 — see §4.1.** I had asserted that `uint64 seq` matches M2's envelope nonce width. The custody session's review of M2 on disk shows the question was wrong: the nonce is `bigint` with no declared width, and it is scoped **per signer and action** where `seq` is **per asset**. `seq` is therefore ruled **not** to be the nonce. What I now assert without a consumer is narrower and more honest: that **nothing in M2 needs to produce `seq` at all**, and that deriving a per-asset sequence is an **operator procedure** T4.4 and T8 must document. The open question for an M2 owner is no longer "how wide is the nonce" but **"does M2 expose per-asset ordering, or must the submitter maintain `seq` itself?"** Nothing on disk answers it.
4. That M9 can anchor `AttestationSubmitted`'s `envelopeHash` as emitted, with no additional field.

**So T0.7 is complete as a specification and explicitly not consumer-reviewed.** I recommend T0.8 stay open rather than be satisfied by my assertion — and that this section be the thing a real M5 owner reviews when they arrive, so the review is a review and not a rubber stamp. **Whether T0.7 may be checkmarked on that basis is a decision for Fahad, not mine** — routed in the thread.

## 9. Decisions routed to Fahad

Per the custody session's instruction, these are **not ruled here** and are logged in the thread whether answered or not.

- **D1 — May T0.7 be checkmarked while T0.8 is impossible?** §8. My recommendation: yes for the spec, with T0.8 left open and §8 as the standing review item.
- **D2 — Is a `Reserved` ADR stub claimed now for the Phase 2 insurer design?** AGENTS.md's claim-by-file rule means the number only exists once committed. Next free is `0028`. My recommendation: yes — Q17 promises "its own ADR", and a reserved stub costs one file and prevents the numbering churn that cost us three renumbers on 2026-10-27.
- **D3 — Does the Tier 1 submitter key differ from the registry's `agent` key, or is it the same key?** ADR `0015` gives both to Tier 1 but does not say whether they are one address. Submitting an attestation and administering an asset are different acts; sharing one key means one compromise does both. My recommendation: separate addresses, same tier.

**Ruled by me, not routed** (technical, recorded for visibility): keeping `BadAttestationSig` declared (§2.1), source-side `seq` rejection (§4), the zeroed-struct requirements (§5), round-down conversion (§6), and conformance-as-abstract-test (§7).
