## P1 — the validator has no warnings, and will not get any

Three questions (Q1, Q3, and implicitly Q6) ask "reject or warn?". Answering that once, first, because it decides them.

**The shared validator returns errors only.** A second severity doubles its API surface and forces **every** consumer — the Foundry script, the console, the tests — to decide independently what a warning means. Two consumers will decide differently, and then a "warning" is a thing the script ignores and the console blocks on, or the reverse. A shared contract exists precisely to stop that.

So: an input is **acceptable or it is not**. Where a human needs to be told something without being stopped, that is the **script's pre-flight print** — which already has exactly this job, from [[T6.0 - Researcher Answers|B1]]: it prints the input's and the envelope's timestamps side by side and *warns* when they differ by more than an hour. Warnings live where there is a human reading output, not in a function returning a boolean.

## Q1 — future `valuationTs`: reject anything after now

**`valuationTs > now` is rejected.** No skew tolerance.

This is deliberately **the same rule as [[T0.6 - Fix Spec (round 2)|D1.2]]** on-chain, where a future timestamp makes clause 4's subtraction underflow into an unnamed `Panic(0x11)`. One rule, both sides of the boundary, so B13 and D1.2 stop being two incidents and become one bug class with one answer. A signed attestation asserting the future is either a broken custodian clock or a forgery; both deserve rejection, and a tolerance δ is a second magic number to defend at a viva for no benefit.

**On the parity cost — accepted, and the alternative is worse.** JSON Schema cannot say "now", so this check is TS-only. The Debugger offers a fixed `maximum: 4102444799` as the schema-expressible alternative. **Reject that:** a hardcoded far-future constant is a magic number that no reviewer can evaluate, it is wrong the moment anyone asks "why 2100?", and it does not actually implement the rule — it permits every one of the next seventy-four years of nonsense. A documented gap beats a guard that looks like a rule and is not one.

The schema's `description` on `valuationTs` must say: *"Must not be in the future; enforced by the TypeScript validator, which JSON Schema cannot express."*

## Q2 — the `uint256` bound: option (a)

**`maxLength: 78` in the schema, exact `BigInt(v) <= 2**256 - 1` in TS.** Applies to `intendedSupply` and `unitValue`.

**Option (b), the generated exact pattern, is rejected on reviewability.** A 78-digit lexicographic regex is unreadable, and **an unreviewable guard is worse than a documented gap** — a reviewer cannot distinguish a correct one from a subtly wrong one, so it buys confidence rather than correctness. `maxLength: 78` catches every absurd value a human would actually type; the two validators then differ only on 78-digit values in the narrow band between `10^77` and `2^256 − 1`, which the schema `description` must state explicitly.

**No cap on `unitValue × intendedSupply`.** The product is not a protocol quantity — nothing on-chain multiplies them, because admission compares **reserve against supply**, never value against anything. A downstream display computing a total should use `bigint` and format it. Inventing a cross-field cap would encode a constraint the protocol does not have, and future readers would hunt for the rule it enforces.

## Q3 — `treasuryWallet == token`: reject

Always a mistake, and an expensive one: minting to the token contract itself puts the entire supply somewhere no one can move it. There is no legitimate case, so there is nothing to warn about (P1). TS-only, same parity note as Q1 — JSON Schema cannot compare two fields.

## Q4 — tighten the `assetId` regex

**`^[a-z0-9]+(-[a-z0-9]+)*$`**, with the 32-character cap kept as a separate `maxLength: 32`.

B3 confirmed the old regex without considering these shapes; the Debugger is right to re-ask. `assetId` is `keccak256`-hashed into the asset's permanent on-chain identity (A1), so **`gold-lot-001` and `gold-lot-001-` are different assets that are indistinguishable to a human** in any log, any table, any screenshot. Trailing and doubled hyphens carry no information and exist only to create look-alike identities. This is the same family as the Cyrillic look-alike the Debugger already tested for.

Splitting the length cap out of the pattern is deliberate: it makes "too long" and "wrong shape" two different messages instead of one confusing one.

## Q5 — `currency` stays format-only

**No allow-list.** The honest reason: an allow-list does not catch the error that matters. A provider who means USD and types EUR passes any allow-list ever written, so the list stops `"XYZ"` while letting the damaging typo through — it buys the appearance of validation.

The real protection is that `currency` is part of `metadataHash` and the provider **confirms the metadata on screen 1** before anything is signed. That is a human checking a human-readable field, which is the only control that catches a plausible-but-wrong value.

Keep: exactly three uppercase letters. Add to the `description`: *"Not checked against the ISO 4217 register; the provider confirms it at onboarding."*

## Q6 — invisible-only strings are rejected

A `description` of a single zero-width space passes the non-empty check, **defeats the guard that already rejects `""`**, and is then hashed into `metadataHash` as the asset's permanent description. To every human it is empty. Reject it.

**Rule:** any free-text field that reaches `metadataHash` — `description`, `valuationBasis.source`, `custodianId` — must contain **at least one character that is not** in Unicode `Cc`, `Cf`, `Zs`, `Zl` or `Zp`. Expressible as a regex in both validators, so **parity holds**.

## Q7 — the path points at the missing field

**`/description`, not `""`.** Likewise `/attestations/0/attestor`.

The brief's E1 is the requirement and the consumer settles it: the console highlights a field **by path**, so the path has to be the field's. Matching Ajv is not a goal in itself — Ajv splits this across `instancePath` plus `params.missingProperty` because it is a general-purpose library that cannot know what its caller will do with either. Our validator has one caller shape and one job.

**Consequence for the harness, not the schema:** the parity comparison must normalise Ajv's `instancePath + missingProperty` into our single path before comparing. That is a harness change. Record it in the harness, or the first CI run after this reports 20 false divergences and someone "fixes" our paths back.

## P2 — commit the parity harness, with Ajv as a devDependency

The Debugger's 80-case parity run is the most valuable thing done on T6.0, and **as a scratch script it is worth nothing by Tuesday** — it proves the two files agreed at one instant, and nothing stops the next edit diverging them. D2 already shows the drift test is too weak to catch it: loosening a `pattern` in one file alone still passes CI today.

**So commit it.** On the dependency objection: `@rwa-vault/types` being dependency-free is a rule about **runtime** dependencies, which is what reaches consumers who import the package. A devDependency exercised only by the package's own test suite reaches nobody. The rule's purpose is preserved; a literal reading of it would cost us the only check that keeps the shared contract shared.

**Requirements:**
1. Ajv 8 as a `devDependency` only. `pnpm --filter @rwa-vault/types test` runs the parity suite.
2. Every brief case plus the Debugger's extras, each asserted to produce the **same accept/reject** from both validators.
3. The three deliberate TS-only checks — Q1 future timestamp, Q3 `treasuryWallet == token`, Q2's 78-digit band — listed in **one explicitly named allow-list constant** in the test, each with a one-line comment citing its Q. Everything not in that list must agree.
4. A **new** divergence therefore fails CI, while the three intentional ones are documented in exactly one place rather than in three people's memories.
5. This **subsumes D2**: with full-case parity, a loosened pattern in one file is caught. Keep the name/required-ness drift test — it fails faster and with a clearer message.

## Addendum — two implementation traps (Debugger, 2026-10-27). Both accepted.

Raised after the rulings above, before any code was written. Both are right, and both are the kind of thing that otherwise surfaces as red CI a day later.

### A1. Q1 makes the validator clock-dependent — inject the clock

"Reject `valuationTs > now`" means the validator reads `Date.now()`, which makes a pure function impure and makes any fixture near the boundary flaky.

**Accepted as proposed:**

```ts
validateOnboardingInput(input, { now?: number })   // now in Unix seconds
// default: Math.floor(Date.now() / 1000)
```

Tests and the parity harness pass a **fixed** `now`; the script and the console omit it and get the real clock. This is the standard remedy and it costs one optional parameter.

**Consequence for P2's allow-list, which the Debugger is right to flag:** Ajv cannot see a clock at all, so the Q1 entry must be scoped as **"every case where `valuationTs > now`"**, not just the year-2100 fixture. Scoping it to the single fixture would let a genuine future-timestamp divergence through the next time someone adds a case.

### A2. Q6's rule is a Unicode property escape — both sides need the `u` flag

"At least one character outside `Cc`/`Cf`/`Zs`/`Zl`/`Zp`" is `\P{...}` syntax, which is silently wrong without `/u`.

**Accepted:**
1. The TS regex **must** carry the `u` flag — without it `\P` is either a syntax error or a literal `P`, and the second failure mode is the dangerous one because it still compiles and still "validates".
2. Ajv 8 compiles patterns with `u` by default, so the schema is fine there. But **JSON Schema does not guarantee `\p`/`\P` support in non-JS validators**, so the field `description` must say *"ECMA-262 pattern with Unicode property escapes"* — the same documented-dependency treatment Q1 and Q2 get for their TS-only parts.
3. **Parity cases required:** ZWSP (U+200B), NEL (U+0085), NBSP-only (U+00A0), and a lone U+FEFF. All four must reject in **both** validators.

Point 2 is worth keeping in mind beyond this batch: it is the first place our schema depends on a regex dialect rather than on JSON Schema proper. If a non-JS consumer ever reads it, this is where it breaks first.

### A3. Harness path comparison — agreed sequencing

The Debugger will normalise Ajv's `instancePath` + `params.missingProperty` into our single path **before** comparing, and will add path comparison when the harness is committed rather than now. Correct order: the current probe compares accept/reject only, so it cannot produce Q7's false divergences, and adding path comparison to an uncommitted script would be work thrown away.

**Work list items 1, 5 and 6 above absorb this addendum.** No new items.
