# ⌨️ → 🧭 T6.0 — Coder Questions, round 2

Built from [[T6.0 - Researcher Answers (round 2)]] plus the later batch-2 additions (providerWallet rename, fineness + grossWeight, eight-field hash list). Every choice below is **PROVISIONAL**: built that way, green, and one edit away from changing. The most consequential are first.

## Questions that change code if answered differently

**R1. `grossWeight` representation — PROVISIONAL.** Built as a `UintString`: gross grams × 10¹⁸, the same encoding and `uint256` bound as `intendedSupply` (so Q2's 78-digit band and its allow-list entry cover it too). Alternative: whole grams or milligrams as a JSON integer. *Why this way:* one numeric convention for every weight in the file, and exact BigInt arithmetic for the relation in R3.

**R2. `fineness` representation — PROVISIONAL.** Built as a JSON integer in **parts per 10,000**, `1..10000` (999.9 fine = `9999`, 995.0 = `9950`). *Why:* every common fineness is exact as an integer, so `grossWeight × fineness / 10000` has no floating point. Alternative: parts per 1,000 with one decimal (`999.9`) is how bars are stamped, but it would be a float in JSON.

**R3. Who enforces `intendedSupply == grossWeight × fineness / 10000` — PROVISIONAL: not the validator.** Your batch-2 message put the derivation and mismatch rejection in the script, so the validator does not check it; a test asserts the fixture satisfies it exactly (remainder 0). Two follow-ups: (a) if you want it in the validator, it becomes a **fourth TS-only allow-list entry** (cross-field, like Q3), so the "three divergences" count changes; (b) should the script reject a gross × fineness that is **not exactly divisible** by 10,000, or round down?

**R4. A2's `abi.encode` types for the two new fields are not specified.** `METADATA_HASH_FIELDS` exports the eight JSON pointers in A2's order (`/assetId`, `/description`, `/grossWeight`, `/fineness`, `/valuationBasis/source`, `/valuationBasis/currency`, `/valuationBasis/unitValue`, `/custodianId`) and a test checks each resolves in the schema. The Solidity types (I would expect `uint256 grossWeight`, and `uint16` or `uint256 fineness`) belong in A2 and maths §6, which are yours. **Neither document has been amended yet**: A2 in [[T6.0 - Researcher Answers]] still lists six fields, and the maths note has no §6.
