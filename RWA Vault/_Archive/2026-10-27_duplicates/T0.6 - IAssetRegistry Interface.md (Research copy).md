## 0. What this is, in reality

The gold bar is in the vault. The custodian has signed for it. Somebody is about to create 1,000 tokens against it.

**The AssetRegistry is the clipboard on the vault door** — the one place that answers *"may anyone mint against this bar, right now?"* Nothing else in the system is allowed an opinion on that.

Four things can be written on it:

| State | In the world |
| --- | --- |
| **UNREGISTERED** | Never heard of this bar. |
| **PENDING** | Someone told us about it. Nobody confirmed the gold. **No tokens.** |
| **LIVE** | Custodian signed, amount covers the mint, valuation fresh. **Tokens allowed.** |
| **FROZEN** | Something is wrong. **Minting stops.** Existing tokens keep existing. |

Plus two numbers per bar: **reserve last attested**, and **tokens in existence**. The gap between them is the entire safety property of the protocol.

**T0.6 prints the blank clipboard.** The boxes, their names, and the exact list of rejection stamps. No logic. You cannot run it. It registers nothing.

**Why that still has to come first:** four separate pieces of code need to talk to this clipboard before it exists — the compliance module asks `isLive` on every transfer (T2.2), the onboarding script calls `register` and `admit` (T6.1a), the console reads `stateOf` (T6.1b), and the input schema needed to know whether an asset's name is text or a hash (T6.0, already built and waiting on exactly this). All four are idle today for want of one file of signatures.

And one reason above the rest: **the rejection stamps are the module's vocabulary.** The sentence a gold dealer reads — *"The gold is worth $2.38M but you asked to mint $2.5M"* — is the onboarding script translating a stamp named `ReserveTooLow`. Rename or invent those names later and every sentence breaks silently, falling back to printing a hex selector at a man holding a gold bar. That is why AC-T06-2 freezes them.

## 2. The state machine

From [[Mathematics - Admission Predicate and Invariants]] §4. The only legal transitions:

```
UNREGISTERED --register----> PENDING
PENDING      --admit ✓-----> LIVE
PENDING      --admit ✗-----> PENDING    (reverts; nothing is written)
LIVE         --admit ✓-----> LIVE       (re-attestation)
LIVE         --freeze------> FROZEN
FROZEN       --unfreeze----> LIVE
```

`enum AssetState { UNREGISTERED, PENDING, LIVE, FROZEN }` — **`UNREGISTERED` must be index 0**, so an unknown id reads as UNREGISTERED out of zeroed storage for free, with no existence flag.

**Three things the maths note leaves implicit, decided here:**

**2.1 A failed `admit` reverts and the asset stays PENDING.** The maths note writes "PENDING → UNREGISTERED/rejected", which would mean a bad signature *deletes* a registration — an honest provider with a stale envelope would lose everything and start over. Wrong. It reverts, nothing is written.

**2.2 Re-attestation on a LIVE asset is allowed** and keeps it LIVE, provided the clauses hold against **current** supply, not the original intended supply.

**2.3 A downward re-attestation is accepted, not refused.** 1,000 tokens outstanding, custodian now says 900 — the bad thing has already happened; the only question is what the contract does. It **accepts the lower figure, blocks further mints, emits `UnderReserve`**, and leaves the freeze decision to an operator. Refusing would leave the chain publishing a reserve the custodian no longer claims — hiding the bad news, which is the opposite of what an attestation is for. Auto-freezing would hand the custodian a denial-of-service switch. This is **Q14** for Fahad with Option B recommended; the interface is buildable either way, since it names the stamps without fixing the rule.

## 3. The interface

### 3.1 Views — anyone may call

```solidity
function stateOf(bytes32 assetId)           external view returns (AssetState);
function isLive(bytes32 assetId)            external view returns (bool);
function reserveOf(bytes32 assetId)         external view returns (uint256);
function attestedSupplyOf(bytes32 assetId)  external view returns (uint256);
function lastSequenceOf(bytes32 assetId)    external view returns (uint64);
function metadataHashOf(bytes32 assetId)    external view returns (bytes32);
function assetRefOf(bytes32 assetId)        external view returns (string memory);
function tokenOf(bytes32 assetId)           external view returns (address);
function assetOfToken(address token)        external view returns (bytes32);  // ** added §18.1 **
function valuationWindowOf(bytes32 assetId) external view returns (uint64);
function attestationSource()                external view returns (address);
```

| Plain words | Function |
| --- | --- |
| What's on the clipboard? | `stateOf` |
| May anyone mint right now? | `isLive` |
| How much gold was last attested? | `reserveOf` |
| How many tokens exist? | `attestedSupplyOf` |
| Which attestation did we last take? (replay guard) | `lastSequenceOf` |
| What metadata did this asset commit to? | `metadataHashOf` |
| What is this bar actually called? | `assetRefOf` |
| Which token belongs to this asset? | `tokenOf` |
| Which asset does this token belong to? | `assetOfToken` — **the reverse view T2.2 cannot work without** (§18.1) |
| How fresh must a valuation be, for *this* asset? | `valuationWindowOf` |

Four of those are deliberate and worth defending:

- **`isLive` is separate from `stateOf`** even though it's derivable. T2.2 calls it on **every transfer**; a one-slot boolean is cheaper than an enum comparison a caller could get backwards.
- **`assetRefOf` is stored, not event-only.** Revision 1 said the slug lived only in the event. That forces the console to run a log indexer just to display a name. One `SSTORE` per asset, once in its life, removes a whole piece of infrastructure from MS1. (At very large scale you would drop it and index events — see §9.6.)
- **`valuationWindowOf` takes an `assetId`** even though MS1 has one global window. §9.2 explains why this is the single most valuable forward-compatibility choice in the file.
- **`attestedSupplyOf` is derived, not stored** — see §3.3.

### 3.2 State-changing — `agent` role (Tier 1 service key, ADR `0015`)

```solidity
function register(bytes32 assetId, bytes32 metadataHash, string calldata assetRef) external;
function admit(bytes32 assetId, uint256 intendedSupply) external;
function freeze(bytes32 assetId, string calldata reason) external;
```

`admit` is **envelope-free** — it reads the attestation from the source (§6). `assetRef` is the human slug; `metadataHash` is computed by the caller per [[T6.0 - Researcher Answers]] A2.

### 3.3 Supply accounting — **there is no token→registry call**

ADR `0014`'s Decision says it in as many words: *"The token itself never references an asset, an assetId, or the registry; it knows only that compliance refused."* So the registry **derives** supply instead of being told:

```
attestedSupplyOf(assetId)  ==  IERC20(tokenOf(assetId)).totalSupply()
```

ADR `0016` (one token per asset) is what makes this exact. No stored counter, no `recordMint`, no `recordBurn`.

**Why this is better, not merely compliant:** a stored counter can drift from `totalSupply` — a missed hook, a direct mint, reentrancy — and a drifted counter makes the invariant *read* as satisfied while being false. A derived view cannot drift. It also keeps the compliance module stateless, which is exactly what ADR `0014`'s "Harder" paragraph warns about.

**Where the invariant is enforced instead — in the compliance module, on the way in:**

> `AssetLiveModule` (or the official `SupplyLimitModule` driven from each attestation) **vetoes a mint when `totalSupply + amount > reserveOf(assetId)`**, and when the asset is not LIVE.

ADR `0014` anticipated this in its own "near-free win" paragraph. So `MintExceedsReserve` belongs to T2.2, not here, and `BurnExceedsSupply` does not exist — a burn cannot break `supply ≤ reserve`.

**Carried forward to T4.5, mandatory:** the invariant fuzzer must drive mints **through the token**. It is now the only enforcement path, so a fuzzer that pokes the registry proves nothing.

### 3.4 Admin — `owner` (2-of-3 multisig, ADR `0015`)

```solidity
function unfreeze(bytes32 assetId) external;                       // ** owner, not agent - ADR 0019 **
function setValuationWindow(uint64 seconds_) external;             // the global default
function setValuationWindowFor(bytes32 assetId, uint64 seconds_) external;  // per-asset override
function setAttestationSource(address source) external;
function setTokenFor(bytes32 assetId, address token) external;
```

## 5. Errors

One per failure, named, never a bare revert — the M1 style rule. **These names are frozen by AC-T06-2**, because [[T6 - Provider Onboarding Console]] §3.4 translates them into the sentences a provider reads and AC-5 asserts them.

```solidity
// --- the admission predicate, clauses 2-4 (clause 1 lives on the source, §6) ---
error StaleSequence(uint64 submitted, uint64 lastAccepted);
error ReserveTooLow(uint256 reserve, uint256 required);
error ValuationStale(uint64 valuationTs, uint64 window);

// --- state machine ---
error AssetNotRegistered(bytes32 assetId);
error AssetAlreadyRegistered(bytes32 assetId);
error AssetNotLive(bytes32 assetId, AssetState state);
error AssetNotFrozen(bytes32 assetId);
error EmptyAssetId();

// --- wiring and authority ---
error NoAttestation(bytes32 assetId);
error TokenNotBound(bytes32 assetId);
error TokenAlreadyBound(address token, bytes32 assetId);   // ** added §18.1 **
error NotAuthorisedAgent(address caller);
error InvalidValuationWindow(uint64 seconds_);
error InvalidAttestationSource(address source);
error AssetIdMismatch(bytes32 expected, bytes32 fromAttestation);
```

**Clause 1's error, `BadAttestationSig`, is declared on `IReserveAttestationSource`, not here** — revision 1 wrongly listed it on the registry. Signature verification happens at submit time, on the source. §3.4 of the T6 note still translates it; only its home changed.

Every clause error **carries its values**, which is what makes an operator sentence possible: `StaleSequence(3, 5)` becomes *"seq 3 is not newer than the 5 we already accepted"*, where a bare `StaleSequence()` becomes *"stale sequence"* and helps nobody.

## 6. The seam (T0.7's two signatures)

`admit` does not take an envelope. It reads the current attestation from a **read-only** source:

```solidity
struct ReserveAttestation {
    bytes32 assetId;      // ** retained - see §14.2 **
    uint256 reserve;
    uint64  seq;
    uint64  valuationTs;
}

function latest(bytes32 assetId) external view returns (ReserveAttestation memory);
function hasAttestation(bytes32 assetId) external view returns (bool);

error BadAttestationSig();   // clause 1
```

**Who verifies the signature, then.** The MS1 implementation gets its own `submitAttestation(bytes envelope)` — **not part of this shared interface** — which verifies the ML-DSA-65 envelope, reverts `BadAttestationSig` if it fails, and stores the decoded struct. M5 implements `latest` straight from the oracle and has no `submitAttestation` at all. That is what makes ADR `0017`'s "M5 replaces the source with no change to AssetRegistry" true rather than nominal: under the earlier design, M5 — an oracle with no envelope — would have had to accept a parameter it deliberately ignores.

**What it costs, stated plainly:**

- **Onboarding becomes two transactions** — submit, then admit — where flow A in [[Decision Algorithms - for Fahad]] shows one. That note is Fahad's; **it is out of date and I have not rewritten it.** §11 carries it as a follow-up awaiting his approval.
- **T6.1a gains one branch** in its idempotency logic: `hasAttestation` true, not yet admitted.
- **Clause 1 is no longer atomic with clauses 2–4.** Not a safety loss — seq-monotonicity and freshness are still checked at `admit`, so a stored-but-stale attestation cannot be admitted — but the Debugger must know.

**What it buys:** an envelope-free `admit`, a real M5 swap, and better errors — `BadAttestationSig` now fails at submit where it is unambiguously about the file, and clauses 2–4 fail at admit where they are about the asset.

Everything else about T0.7 — the custodian key registry, how M5 satisfies `latest`, Q11's attestor-set shape — is T0.7's own research.

## 9. Does this scale? — the forward-compatibility analysis

The question that matters for an interface is not "does it work" but "what breaks it later". Each row is a thing that *will* happen.

**9.1 More assets — 1, then 50, then 500.** Everything is keyed `mapping(bytes32 => …)`. O(1) per asset, no loops, no growth in any function's gas. **There is deliberately no `getAllAssets()`** — an on-chain array means an unbounded loop and eventually a function nobody can call. Enumeration comes from `AssetRegistered` events, off-chain.

**9.2 More asset classes — gold, then T-bills, then a REIT.** This is why `valuationWindowOf(bytes32 assetId)` takes an id. Gold revalues daily; a REIT revalues quarterly. A global `valuationWindow()` would have to become per-asset later, and **changing a getter's signature breaks every caller** — the module, the script, the console, the tests. Taking the id now costs nothing today (it returns the global default until an override is set) and converts a future breaking change into a configuration change. **Highest-value decision in the file.**

**9.3 Q11 — the insurer co-signs.** Changes nothing here. The registry only calls `latest()`; whether one party signed or three is entirely the source's business. This is the payoff of the read-only seam in §6, and it is why that correction was worth taking.

**9.4 M5 replaces the reserve source in Phase 2.** `setAttestationSource(address)` — one transaction from the multisig. No migration, no redeploy, no storage move.

**9.5 Someone eventually wants two tokens for one asset.** Out of scope by ADR `0016`, and the interface says so: `tokenOf` returns a single address. If that ever changes it is a real interface break — `tokensOf`. Flagged honestly rather than pre-built, because speculative plural APIs are how interfaces rot.

**9.6 Storage growth from `assetRefOf`.** One string slot per asset, written once. At 500 assets this is irrelevant. At a scale where it isn't, drop the getter and index `AssetRegistered` instead — a removal, not a redesign.

**9.7 Upgradeability.** Interfaces are proxy-agnostic: no constructor, no storage, no initializer. So T0.6 is safe whichever way T4.1 goes. **But no ADR covers this**, and upstream T-REX is proxy-based — see §10.

**9.8 `uint64 seq` and `uint64 valuationTs`.** `valuationTs` as `uint64` is safe past the year 500 billion. `seq` at `uint64` allows ~18 quintillion attestations per asset. The open item is whether **M2's envelope nonce is ≤ 64 bits** — T0.7 must confirm before T4.4, or the decode truncates silently.

## 10. My questions

**Blocking: none.** This task can be built the moment the Coder picks it up.

**One non-blocking question, for Fahad — and it is not a T0.6 question:**

> **Are M3's contracts upgradeable (proxy-based) or immutable?**
>
> No ADR covers it. It matters because Tokeny's upstream T-REX is proxy-based with an implementation authority, and ADR `0012` has us vendoring part of that stack while building the rest — so we may end up with proxies on one half and plain deploys on the other without ever having decided to. It changes T4.1's shape (initializer vs constructor, storage gaps), T5.1's deploy script, and whether a bug in the admission predicate is fixable without migrating every holder.
>
> **Recommendation: immutable for MS1.** The registry has an owner-settable attestation source and valuation window already, which covers the changes we actually expect; a proxy adds an upgrade key that is itself an audit finding. Record as an ADR either way, because "we never decided" is the worst answer to this at a defence.
>
> **Does not block T0.6** — interfaces are proxy-agnostic (§9.7). Should be answered before **T4.1**.

I will raise it as **Q15** in [[Open Questions for Fahad]] rather than leave it in a research note where it can be missed.

### 18.1 The gap is real — adding `assetOfToken`

`IModule.moduleCheck(from, to, value, compliance)` hands the module a **compliance address**. `IAssetRegistry` mapped `assetId → token` and nothing the other way, so `AssetLiveModule` could reach the token (`getTokenBound()`) but could never learn **which asset it is looking at** — and therefore could not call `isLive(assetId)` or `reserveOf(assetId)` at all. The invariant ADR `0014` moved into the compliance module had, literally, nowhere to be computed.

**Decision: option (a). Add `assetOfToken(address token) external view returns (bytes32)`**, maintained by the same `setTokenFor` write, plus `error TokenAlreadyBound(address token, bytes32 assetId)` so the bijection cannot be broken by binding one token to two assets.

Three reasons (a) over (b):

1. **ADR `0016` makes the mapping a bijection** — one token per asset. A reverse view is therefore exactly as authoritative as the forward one and derived from the same single write. It is not a second source of truth; it is the same truth read backwards.
2. **Option (b) reintroduces the drift we deliberately removed.** A module holding its own `compliance → assetId` config is a second binding that can disagree with `registry.tokenOf`. That is the same "two numbers that must agree" failure that got `recordMint` deleted in §9. The Debugger's own mitigation — assert `tokenOf(assetId) == getTokenBound()` on every check — is a cost paid forever to detect a problem (a) prevents.
3. **`IModule.isPlugAndPlay()` exists as a first-class concept** in the interface we already scaffolded. A module needing per-deployment configuration cannot honestly return `true`, and ADR `0014`'s whole premise is a module that can be bound and replaced at runtime through `ModularCompliance`. Option (b) quietly gives that up.

This is a change to frozen names under AC-T06-2, which is why it is mine and not the Debugger's. **Counts become 11 views and 15 errors.**

### 18.2 The ordering requirement is real — it belongs to T3.1

The Debugger is right that the arithmetic is only correct if the token calls `canTransfer` **before** `_mint` updates `totalSupply`. If the mint lands first, `totalSupply` already includes `value` and the cap check compares the post-mint supply against the reserve, silently permitting one mint's worth of over-issuance at the boundary.

T-REX orders it that way, but we are building the token in-house (ADR `0012`), so **this is an assumption on our own code and it gets written down as a requirement, not inherited as a habit:**

> **Carried to T3.1's research as a hard requirement.** `Token.mint` must call `compliance.canTransfer(address(0), to, value)` **before** `_mint`. T3's acceptance criteria must include a test that fails if the order is reversed — not a comment saying it matters. The natural test: a mint of exactly `reserve - totalSupply + 1` must revert.

### 18.4 The documentation contradiction — **FROZEN blocks minting only**

The Debugger found four documents disagreeing about whether a holder of a FROZEN asset may transfer:

| Source | Says |
| --- | --- |
| ADR `0014` Decision | module vetoes "any mint **or transfer**" when not LIVE |
| `freeze` natspec (mine) | "minting stops, existing tokens remain" |
| ADR `0021` | stale reserve freezes **minting only**; transfers continue |
| `packages/types/src/index.ts:31` | FROZEN = no "minting, redemption, or borrowing" |

**Ruling: FROZEN blocks minting. Transfers continue.** ADR `0014`'s "or transfer" is the odd one out and is superseded on this point by ADR `0019` decision 6.

The reasoning, which is the same reasoning ADR `0021` already accepted for staleness:

- **The usual trigger for FROZEN is the custodian's problem, not the holder's.** A stale valuation or a reported shortfall is something done *to* holders. Blocking their transfers takes away their only way out, as a penalty for someone else's failure, and it is a liveness cost extracted by a third party's inaction — the centralisation vector this project otherwise works to remove.
- **Halting transfers already has a mechanism, and it is `pause()`.** ERC-3643 gives us a token-level pause for the systemic case and per-wallet freeze for the targeted one. Making asset-FROZEN *also* stop transfers duplicates `pause` while removing the operator's ability to choose between the two. Three overlapping brakes is worse than two distinct ones.
- **Minting is the only action that increases the claim on the reserve.** Blocking exactly that is the minimal correct response to uncertainty about the reserve's size. Everything else is collateral.

`AssetLiveModule` therefore vetoes **only** when `from == address(0)` and the asset is not LIVE. A FROZEN asset's holders transfer normally.

- **Fixture unit sweep → 🧭, one real question.** `unitValue` 130e18 per gram is unit-correct and the right order of magnitude ✓, and `intendedSupply` 1000e18 = 1000 g ✓. But:
  1. **Fine or gross?** ADR `0020` says one token = one gram of **fine** gold, *and* "a 1 kg lot mints 1,000 × 10¹⁸". Those agree only for pure gold. A real 1 kg bar is 999.9 fine, so it holds **999.9 g fine**. If the custodian attests reserve in fine grams (which is what the token claims to represent), then admission of the fixture lot is `999.9e18 ≥ 1000e18` → **`ReserveTooLow` for an honest bar**. If supply is instead minted on gross weight, every token over-claims fine gold by 0.01%. The ADR must say which weight `reserve` and `intendedSupply` are in. My view is that `intendedSupply = fine weight`, i.e. `999.9e18` for this bar, but it is a custody decision.
  2. **The fixture's description is factually wrong**: "1kg LBMA Good Delivery bar". LBMA Good Delivery gold bars are ~350–430 oz (~11–13 kg); a 1 kg bar is a *kilobar*. This is harmless in a test, but the string is hashed into `metadataHash`, and the §3.2 fixture is the template providers will copy. Suggest "1kg kilobar, 999.9 fine, serial XAU-88213". That also carries the fineness the supply depends on.
