## 0. What is actually being fixed, in reality

One bug, and it is the serious one.

`AssetLiveModule` is the piece that stops someone minting tokens when there isn't enough gold. When it gets called, it's handed a **compliance contract's address** — and nothing else. From that it can find the token. But the registry only knew `asset → token`, never the reverse, so the module **could not work out which gold bar it was looking at**. It could not ask "is this asset live?" or "how much gold is attested?", because it had no asset id to ask about.

So the one rule that makes the word *backed* mean anything — **tokens in existence ≤ gold attested** — had nowhere to run. Not "was implemented wrongly": had **no possible home**.

The fix is one new view, `assetOfToken`, plus the guards that keep it honest. Everything else below is the Debugger's sweep catching smaller things while the file is open — and the file being open is the cheapest moment any of them will ever be fixed, because four tasks are about to compile against these names.

## 2. A5 — rename `TokenBound` → `AssetTokenBound`

`IModularCompliance.TokenBound(address)` already exists. Ours was `TokenBound(bytes32, address)`. The topic0s differ, so the ABI is unambiguous — but **consumers filter by event name, not by topic hash.** T6.1b's viem `parseEventLogs({ eventName: "TokenBound" })` over a merged ABI, or any indexer keyed on names, gets two different shapes under one label.

Renaming costs one line now. Leaving it costs a debugging session later in a place where the symptom (an event decoding with the wrong fields) points nowhere near the cause. **Rename.**

## 3. B4 — bound the valuation window

`setValuationWindow(type(uint64).max)` is accepted as specified, and it **silently disables admission clause 4 forever**. A safety property turned off by a plausible typo, with no error and no event to distinguish it from intent.

**Decision:** `setValuationWindow` and `setValuationWindowFor` revert `InvalidValuationWindow(seconds_)` unless `0 < seconds_ ≤ 365 days` (31,536,000).

The cap is deliberately generous rather than policy-shaped. Its job is to stop *accidental disabling*, not to pre-empt Q13: 24 h (gold), 90 days (a REIT, per Q13 option C) and anything else a real asset class needs all fit comfortably. A window beyond a year means "never stale", which should require an interface change and an ADR, not a setter call.

## 4. C7 — `attestedSupplyOf` reverts when no token is bound

`attestedSupplyOf` derives from `IERC20(tokenOf(assetId)).totalSupply()`. With no token bound there is no number to derive.

**Decision: revert `TokenNotBound(assetId)`.** Returning `0` would be indistinguishable from *"a live asset with nothing minted yet"* — so a misconfigured asset would display "0 tokens issued", which is a **wrong fact** rather than a visible error. A view that cannot answer must say so.

**For T6.1b:** check `stateOf` (or `tokenOf != address(0)`) before calling it. A PENDING asset has no supply to show anyway, so the guard costs the console nothing. This must be in the NatSpec.

## 5. `assetOfToken` semantics — the three gaps

**5.1 Unbound token → `bytes32(0)`.** Confirmed, and worth documenting as *intended* rather than incidental: `assetOfToken(unknown)` returns zero, `stateOf(bytes32(0))` is `UNREGISTERED`, `isLive` is `false`, so the module **fails closed**. A module that cannot identify its asset refuses the mint. That is the correct direction for a safety check to fail, and the NatSpec must say so explicitly, or a later reader will "fix" it into a revert and change the failure mode.

**5.2 Re-binding an asset to a different token — forbidden.** The Debugger is right that `TokenAlreadyBound` only stops *one token → two assets*, and leaves *one asset → two tokens* open. If `setTokenFor(asset, newToken)` were allowed without clearing the old reverse entry, the **old token would still resolve to the asset and still pass the module's check** — a silently broken bijection and a live over-issuance path.

Two ways to close it: clear-on-rebind, or forbid. **Forbid**, with `error AssetAlreadyHasToken(bytes32 assetId, address token)`.

Clear-on-rebind means a correct implementation must remember to delete the reverse entry — exactly the "must remember" class of bug the derived-supply design was chosen to eliminate (§3.3). Forbidding makes a token migration an explicit future ADR rather than an accidental capability of a setter. ADR `0016` is one token per asset; this makes it true in the code rather than in prose.

**5.3 `setTokenFor(asset, address(0))` — rejected.** `error InvalidTokenBinding(address token)`. Unbinding has no use case (an asset with a live token cannot lose it without orphaning holders), and permitting it would make `assetOfToken`'s zero return ambiguous between "never bound" and "deliberately unbound".

## 6. D1.1 — agent management belongs in the interface

`NotAuthorisedAgent` existed with no way to *become* an agent. T5.2 has to grant that role and T4.1 has to store it, so the capability exists either way — the only question is whether it is named here or left to the concrete type.

**Decision: name it here.** Add `isAgent(address) view`, and `addAgent(address)` / `removeAgent(address)` as **owner** functions, with `AgentAdded` / `AgentRemoved` events.

**And do not inherit OpenZeppelin `AccessControl`.** It is available, but it would revert `AccessControlUnauthorizedAccount` — a name that is **not in [[T6 - Provider Onboarding Console]] §3.4's translation table**, so the onboarding script would print a hex selector at a provider for the single most likely operational error. It also brings a role-admin hierarchy we have no use for: ADR `0015` fixes exactly two roles, an owner multisig and an agent service key. Two roles do not need a role framework. T4.1 implements a minimal agent mapping, in the shape of T-REX's `AgentRole`, and keeps our named error.

## 7. D1.2 — a future `valuationTs` must be a named rejection, not a panic

Clause 4 is `now − valuationTs ≤ τ`. If `valuationTs > block.timestamp`, that subtraction **underflows and reverts `Panic(0x11)`** under Solidity 0.8 — an unnamed arithmetic panic the onboarding script cannot translate, breaking AC-5 at exactly the moment a provider most needs a sentence.

**Decision: add `error ValuationInFuture(uint64 valuationTs, uint64 blockTime)`.** T4.1 must check `valuationTs <= block.timestamp` **before** subtracting.

**No clock-skew tolerance.** A signed attestation asserting a future valuation is either a broken custodian clock or a forgery; both deserve a named rejection rather than silent acceptance, and a tolerance δ is a second magic number to defend at a viva for no gain.

This is the on-chain twin of T6.0's **B13**, which I predicted in that brief and which the Debugger is still checking off-chain. Same bug, both sides of the boundary — worth noting in the report as a class, not two incidents.

## 8. D6 — the module returns `false`; AC-5 is rescoped

The Debugger is right and it corrects my own brief: `IModule.moduleCheck` returns `bool`, so a veto reaches the token as a generic compliance failure. `AssetNotLive` is **not** what a blocked mint surfaces, which means the T0.6 brief's claim that it is "the error T2.2's veto will raise most often" was wrong.

The Debugger notes a module *could* revert with the registry's error instead, and that it would work mechanically. **Decision: it must not.**

`ModularCompliance.canTransfer` fans out across modules and is also the **pre-flight read** T6.1b uses to render its four ticks before submitting. A module that reverts would abort the whole fan-out — one module's veto would prevent the others from being evaluated, and a pre-flight "would this succeed?" check would revert instead of returning `false`. That breaks the console's ability to show *why* something will fail, which is the very thing the named errors exist for.

**So specificity comes from a pre-flight read, not from the revert:**

- **The `admit` path keeps named errors.** The registry reverts `StaleSequence` / `ReserveTooLow` / `ValuationStale` / `ValuationInFuture` directly, and §3.4's translation table applies in full.
- **The `mint` path gets its sentence from reading first.** T6.1a and T6.1b call `isLive(assetId)` and `reserveOf(assetId)` and compare before submitting, then say exactly which condition fails. The on-chain revert stays the token's generic compliance error — which is ADR `0014`'s documented "Costly" consequence, now concrete.

**Carried to [[T6 - Provider Onboarding Console]]:** AC-5's named-error assertions apply to the admission path. The mint path needs its own criterion — that the pre-flight names the failing condition before any transaction is sent. I will add it as **AC-21** when I next touch that note.

### 14.1 The vacuous assertions — a correction to my own §13.3

In §13.3 I praised the Coder's A5 test as better than my spec. That was **half right, and I should have checked it rather than reasoning about it.**

- Lines 153–154 *are* the real guard: they tie each signature string to `IAssetRegistry.AssetTokenBound.selector` and `IModularCompliance.TokenBound.selector`, so a rename breaks the build.
- Lines 155–156 compare **two string literals to each other**. `keccak256("AssetTokenBound…") != keccak256("TokenBound…")` is true at compile time, forever, regardless of what the contracts say. It can never fail.

**A test that cannot fail is worse than no test**, because it reads as coverage in a file whose whole purpose is to stop a guard silently stopping guarding — which is precisely the A5 failure mode. Delete 155–156 and assert `IAssetRegistry.AssetTokenBound.selector != IModularCompliance.TokenBound.selector`, which is a real comparison of two real declarations.

The merged-ABI name-uniqueness check does belong in **T0.9**, as the Debugger says: Solidity cannot see a third contract's ABI.

### 14.2 `MAX_VALUATION_WINDOW` as a file-level constant — adopted

The Debugger's refinement is better than my T4.1-only plan and I am taking it, even though it touches the frozen file:

> A **file-level** `uint64 constant MAX_VALUATION_WINDOW = 365 days;` in `IAssetRegistry.sol`. The *interface* cannot hold a constant; the *file* can. NatSpec then references `{MAX_VALUATION_WINDOW}` instead of repeating the number, and the interface test pins it with `assertEq(MAX_VALUATION_WINDOW, 365 days)`.

Plus, carried to T4.1: both setters validate against the constant; tests bind to it (`MAX` accepted, `MAX + 1` and `0` revert `InvalidValuationWindow`, both setters); a fuzz test asserting success **iff** `0 < w ≤ MAX`; and a **no-literal rule** — a setter with its own hardcoded `365 days` passes every boundary test while being a second source of truth, which is the drift this constant exists to prevent.

### 14.3 The four spec points

**1. No named error for a non-owner call — add `NotOwner(address caller)`.**

The Debugger has caught me being inconsistent. I rejected OpenZeppelin `AccessControl` in §6 precisely because `AccessControlUnauthorizedAccount` is absent from [[T6 - Provider Onboarding Console]] §3.4's translation table — and then left the owner path to inherit `Ownable` and produce `OwnableUnauthorizedAccount`, which fails in exactly the same way. Same objection, same answer: **`NotOwner(address caller)` is declared here, and T4.1 implements a minimal owner check rather than inheriting `Ownable`.** Two roles still do not need a framework.

**2. `addAgent` / `removeAgent` edge cases — revert, never no-op.**

- `address(0)` → `InvalidAgent(address account)`.
- Adding an existing agent, or removing an address that is not an agent → `AgentUnchanged(address account)`.

**Not idempotent, deliberately.** These are 2-of-3 multisig operations. A silent no-op means the multisig signed a governance action that did nothing, emitted no event, and left no way to tell whether the intended change happened — so the operator's only recourse is to read state back and guess which of the two signers misunderstood. A revert makes the outcome unambiguous at the cost of one retry.

**3. `addAgent` / `AgentAdded` byte-identical across registry and token — accepted, goes to T5.2.**

Real risk, and a nasty one: a T5.2 call to the wrong address **succeeds silently**. The Debugger's rule is adopted as a T5.2 requirement — after granting, read `isAgent` back on the intended contract **and assert it is false on the other**. A deploy script that cannot tell which contract it configured is not a deploy script.

**4. A default window of `0` rejects every admission — state it, and take it in the constructor.**

Both accepted. It fails closed, which is correct and must stay, but "correct by accident of zero-initialisation" is not documentation. NatSpec on `valuationWindowOf` states it; **T4.1's constructor takes the window as an argument** so a deployment cannot exist in the all-rejecting state.

### 15.1 Which substance? — add the generic rule, not the gold answer

On disk: `reserveOf` says *"in token base units"*, and the source's struct says *"in token base units (same unit as totalSupply)"*. That is **unit-consistent** — reserve and supply are compared in the same unit, which is what `0020` needs — but it never says **which substance**, so the ambiguity is simply relocated to whoever implements the source (T4.4, later M5).

The Coder's instinct not to write "fine grams" into the interface is right, and the reason is ADR `0016`: one token per asset means a T-bill or a REIT token uses **this same interface** with its own unit entirely. Hardcoding gold into an asset-agnostic interface would be a different bug.

**Ruling: state the invariant generically, add the prohibition, cite the example.**

> `reserve`, `intendedSupply` and `attestedSupply` are all in **the token's own base units** and must never be mixed with any other measure of the same asset. For gold that unit is **fine grams × 10¹⁸** (ADR `0020`); gross weight never appears.

The operative clause is **"must never be mixed with any other measure of the same asset"** — that survives every asset class, where "gross weight never appears" only happens to be true of metal. The gold line is an example, clearly cited, not the rule.

### 15.2 The fineness field and `metadataHash` must move together

A real sequencing trap, and the Coder is right to raise it before batch 2 rather than after.

[[T6.0 - Researcher Answers|A2]]'s canonical encoding lists exactly six fields. If batch 2 adds `fineness` to the schema and the recipe is not amended in the **same change**, then the field exists but is **not committed on-chain** — and my own argument for adding it ("in prose, the permanent record cannot be checked against the supply it determined") stays true of the hash. The field would be decoration.

**Ruling: schema field and hash recipe land in one change, and `grossWeight` comes too.**

Committing fineness alone lets a third party verify the fineness but **not re-derive the supply**. Committing `grossWeight` as well makes `intendedSupply = grossWeight × fineness` fully recomputable from committed data by anyone — which is the whole property being bought. One extra field for a complete check instead of a partial one.

So A2 becomes **eight** fields: `assetId`, `description`, `grossWeight`, `fineness`, `source`, `currency`, `unitValue`, `custodianId`. [[Mathematics - Admission Predicate and Invariants]] §6 is amended in the same commit.

**Acceptance criterion for batch 2:** a test asserts `intendedSupply == grossWeight × fineness` for the fixture, and the hash recipe's field list is asserted against the schema's — so the two cannot drift.

### 15.3 `intendedSupply`'s unit — same one-phrase fix

`admit`'s `@param intendedSupply the supply clause 3 must cover on first admission` never says base units. Low risk, since clause 3 compares it directly against `reserve`, but it is the same omission as §15.1 and gets the same phrase.
